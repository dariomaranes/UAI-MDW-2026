UI y design system

Objetivo

Que el sistema se vea como un producto y no como un trabajo práctico. Hoy la IA genera interfaz mejor que nunca: lo que se aprende es a curar lo que genera.

  • 5 min Standup
  • 5 min Metodología: APIs, API First, REST y JSON
  • 25 min Sistema de diseño · Tailwind · accesibilidad
  • 15 min Demo: generar un componente y curarlo
  • 50 min Taller: el flujo principal, navegable y presentable
  • 15 min Code review + prueba de usabilidad con otro equipo
  • 5 min Cierre
Esto que leyeron, hoy lo hacen así

La lectura es sobre API First. Fíjense lo que pasó sin darse cuenta: construyeron la API antes que cualquier pantalla, así que hoy la interfaz consume un contrato que ya existía. Eso es API First, y es la razón por la que mañana podrían hacer una app móvil sin tocar el backend. Además hoy se auditan los criterios de usabilidad y accesibilidad que escribieron en la clase 2: al cierre de la clase, alguien de otro equipo usa el sistema sin que le expliquen nada, y ustedes anotan en silencio dónde se traba.

1. Un sistema de diseño es un conjunto de decisiones tomadas una vez

Una interfaz se ve amateur no por fea, sino por inconsistente: seis azules distintos, botones de cuatro alturas, espaciados al azar. Cada uno de esos es una decisión que se volvió a tomar cada vez.

Un sistema de diseño fija de antemano estas cinco cosas:

DecisiónRegla práctica para este proyecto
ColorUn color de marca, uno de peligro, y grises. Nada más
TipografíaUna familia, tres tamaños (título, texto, chico)
EspaciadoLa escala de Tailwind (4, 8, 16, 24…). No inventar valores
Bordes y sombrasUn radio y una sombra para todo el sistema
ComponentesUn solo Button, con variantes. No cinco botones distintos

Por qué Tailwind y no CSS suelto

  • Las clases están limitadas a una escala: es difícil ser inconsistente sin querer.
  • El estilo vive al lado del marcado: no hay que buscar en qué archivo estaba.
  • No hay nombres de clase que inventar ni CSS muerto que nadie se anima a borrar.
  • Es lo que mejor generan los asistentes, porque no dependen de un archivo que no ven.

shadcn/ui: componentes que se copian, no se instalan

shadcn no es una librería: es un catálogo de componentes accesibles que copian al repositorio y editan. Eso importa por dos razones: pueden adaptarlos sin pelearte con la librería, y son código propio que también hay que poder explicar.

npx shadcn@latest init npx shadcn@latest add button input card dialog form table

2. Accesibilidad: el mínimo que se evalúa

No es un extra de fin de curso: es la diferencia entre una interfaz que funciona para todos y una que funciona para quien la programó.

  • Todo se puede usar con el teclado: Tab llega a todos lados y se ve dónde está el foco.
  • Todo input tiene su <label> asociado. Un placeholder no es una etiqueta.
  • Los botones son <button> y los links son <a>. Un div con onClick no existe para un lector de pantalla.
  • El contraste de texto es suficiente (gris clarito sobre blanco, no).
  • Las imágenes tienen alt; las decorativas, alt="".
  • El error de un formulario se dice con texto, no solo pintando el borde de rojo.
Prueba de 30 segundos

Guarden el mouse y recorran su flujo principal solo con el teclado. Si no pueden completarlo, la accesibilidad está rota — y probablemente también lo esté para alguien que usa el sistema todo el día y quiere ir rápido.

3. Qué le pedimos a la IA (y qué no)

La UI es donde más rinde la IA… y donde peor se acumula

Genera pantallas enteras muy rápido. El problema es que cada pantalla generada por separado inventa su propio criterio: otro azul, otro espaciado, otro botón. En tres clases tienen cinco sistemas de diseño conviviendo.

Antídoto: generen contra los componentes que ya tienen. "Usen el Button y el Card que están en components/ui. No agregues colores nuevos: solo los del tema."

Deleguen

  • Maquetar una pantalla a partir de un boceto
  • Hacer responsive algo que no lo es
  • Estados de carga, vacío y error
  • Revisar accesibilidad de un componente

Decidan ustedes

  • La paleta y la tipografía
  • Qué información va primero en la pantalla
  • Cuál es la acción principal de cada vista
  • Qué se muestra cuando no hay datos

4. Taller

  1. Fijar el tema: colores, tipografía y radio en globals.css. Instalar shadcn y los componentes base.
  2. Dejar el flujo principal completo navegable: listado, detalle y la acción principal. Consistente, responsive y con los tres estados (carga, vacío, error).
  3. Pasada de accesibilidad con la checklist de arriba.
  4. Probar en un celular real, no en el simulador del navegador.

Cierre: prueba de usabilidad con otro equipo

  1. Una persona de otro equipo se sienta frente al sistema en producción.
  2. Le dicen solo la tarea: "reservá un turno para mañana". Nada más.
  3. Ustedes no hablan. Anotan dónde duda, dónde hace clic mal, qué no encuentra.
  4. Los 3 hallazgos principales se convierten en issues del repo.
Lo más difícil del ejercicio

Quedarse callado. Cada vez que sientas la necesidad de explicar algo, eso mismo es un problema de diseño: el usuario real no va a tener a nadie al lado.

Entregable de la clase

  • Tema definido y aplicado: colores, tipografía y espaciado consistentes.
  • Flujo principal navegable de punta a punta, responsive.
  • Estados de carga, vacío y error en todas las pantallas del flujo.
  • Checklist de accesibilidad cumplida.
  • 3 hallazgos de la prueba de usabilidad, convertidos en issues.
