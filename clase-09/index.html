La lectura es sobre MVC. 1. La pregunta que ordena todo: ¿dónde corre esto?

En Next.js con App Router, un componente es Server Component por defecto. Solo se vuelve Client Component si ustedes escriben "use client" arriba.

Server Component (por defecto)

  • Corre en el servidor, nunca llega al navegador
  • Puede leer la base directamente, sin pasar por HTTP
  • Puede usar secretos
  • No pesa nada en el bundle del cliente
  • No puede usar useState, onClick ni nada del navegador

Client Component ("use client")

  • Corre en el navegador
  • Puede usar estado, efectos y eventos
  • Puede acceder a window, localStorage
  • Suma peso al bundle
  • Nunca puede tocar la base ni ver un secreto
El error que va a cometer el equipo esta clase

Poner "use client" arriba de una página entera porque un botón necesita onClick. Eso manda toda la pantalla al navegador, incluida la parte que leía datos.

Lo correcto: la página sigue siendo server, y el botón se extrae a su propio componente cliente. La frontera se empuja lo más abajo posible en el árbol.

app/(app)/turnos/page.tsx ← Server: lee la base └── <ListaTurnos turnos={...} /> ← Server: solo muestra └── <BotonCancelar /> ← "use client": tiene onClick Solo el botón viaja al navegador. El resto se renderiza en el servidor y llega como HTML.

2. Los hooks, desde el problema que resuelven

HookProblema que resuelveCuándo NO usarlo
useState Un valor que cambia por interacción del usuario y hay que redibujar Para datos del servidor. Para eso está el Server Component o TanStack Query (clase 12)
useEffect Sincronizar con algo fuera de React: un timer, una suscripción, el DOM Para traer datos. Es el uso más común y casi siempre el peor
useMemo Un cálculo caro que se repite en cada render "Por las dudas". Optimizar sin medir agrega complejidad y no gana nada
useRef Guardar algo entre renders sin redibujar, o apuntar a un nodo del DOM Para estado que sí debe redibujar
Por qué useEffect + fetch quedó viejo

Ese patrón —que era el patrón hace unos años— obliga a: renderizar vacío, esperar a que llegue el JS, pedir los datos, renderizar de nuevo. Cuatro pasos y una pantalla en blanco en el medio. Un Server Component ya llega con los datos adentro.

Ojo con esto cuando le piden código a una IA: mucho material de entrenamiento es de la época anterior. Si les devuelve useEffect para cargar datos en una página, probablemente esté resolviendo el problema de 2021.

3. Estructura de rutas

app/ (public)/ ← grupo de rutas sin sesión login/page.tsx (app)/ ← grupo de rutas con sesión layout.tsx ← acá se verifica la sesión UNA vez turnos/ page.tsx ← /turnos [id]/page.tsx ← /turnos/abc123 loading.tsx ← se muestra mientras carga error.tsx ← se muestra si algo explota api/ ← los endpoints de la clase 4 Los paréntesis agrupan sin aparecer en la URL.

loading.tsx y error.tsx no son opcionales en este proyecto: la rúbrica del Parcial II mira explícitamente que los estados de carga y error estén resueltos.

4. Qué le pedimos a la IA (y qué no)

Deleguen

  • Componentes de presentación a partir de una descripción
  • El layout, la navegación, el esqueleto de las rutas
  • Convertir un mockup en JSX
  • Estados de carga y error

Decidan ustedes

  • Qué es server y qué es cliente
  • Dónde va la frontera "use client"
  • Qué datos necesita cada pantalla
  • Cómo se compone la jerarquía de componentes
Regla de revisión para esta clase

Cada vez que vean un "use client" nuevo en un diff, pregúntense: ¿qué necesita este componente del navegador? Si no saben contestarlo, sobra.

5. Taller

  1. Estimar y anotar en el repo: ¿cuántas clases nos lleva el frontend? ¿qué es lo más riesgoso?
  2. Layout de la aplicación: navegación, indicador de usuario logueado, logout. La sesión se verifica en el layout.tsx del grupo (app).
  3. La pantalla principal: listado real desde la base, como Server Component. Con loading.tsx, error.tsx y estado vacío ("todavía no hay nada, creá el primero").
  4. Una interacción de cliente aislada en su propio componente (un filtro, un botón de detalle) y contar cuántos "use client" quedaron. Si hay más de dos, revisar.

Entregable de la clase

  • Layout con navegación y sesión verificada en el servidor.
  • Listado principal con datos reales, renderizado en el servidor.
  • Estados de carga, error y vacío resueltos.
  • Los "use client" son mínimos y cada uno está justificado.
  • Las observaciones del Parcial I, convertidas en issues del repo.
