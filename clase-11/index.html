1. Un formulario tiene cuatro estados, no uno

INICIAL ──► ENVIANDO ──► ÉXITO │ └──► ERROR ──► (vuelve a INICIAL, sin perder lo escrito)

Cada estado tiene su comportamiento, y los tres últimos son los que se olvidan:

EstadoQué tiene que pasarQué sale mal si no lo hacen
InicialCampos vacíos o con los valores actuales al editar—
EnviandoBotón deshabilitado, indicador visibleEl usuario hace doble clic y se crean dos registros
ÉxitoConfirmación clara y redirección o limpiezaEl usuario no sabe si funcionó y lo hace de nuevo
ErrorMensaje entendible sin perder lo que escribióPierde 10 campos completados. Es la peor experiencia posible

2. Un solo schema, dos usos

El mismo crearTurnoSchema que valida en el endpoint valida en el formulario. No se duplican reglas: si mañana el título pasa a 200 caracteres, se cambia en un solo lugar.

"use client"; import { useForm } from "react-hook-form"; import { zodResolver } from "@hookform/resolvers/zod"; import { crearTurnoSchema, type CrearTurnoInput } from "@/lib/schemas/turno"; export function FormularioTurno() { const { register, handleSubmit, formState: { errors, isSubmitting }, } = useForm<CrearTurnoInput>({ resolver: zodResolver(crearTurnoSchema), // ← el MISMO schema del servidor }); async function onSubmit(datos: CrearTurnoInput) { const respuesta = await fetch("/api/turnos", { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify(datos), }); if (!respuesta.ok) { // El servidor validó de nuevo: puede rechazar por una regla de negocio // que el cliente no puede conocer (ej: turno superpuesto → 409). const error = await respuesta.json(); throw new Error(error.error); } } return ( <form onSubmit={handleSubmit(onSubmit)}> <label htmlFor="fecha">Fecha</label> <input id="fecha" type="datetime-local" {...register("fecha")} /> {errors.fecha && <p role="alert">{errors.fecha.message}</p>} <button type="submit" disabled={isSubmitting}> {isSubmitting ? "Guardando…" : "Guardar"} </button> </form> ); }
Validar en el cliente no reemplaza validar en el servidor

La validación del cliente es comodidad: feedback inmediato sin ir y volver. La del servidor es seguridad. Las dos usan el mismo schema, pero solo una es obligatoria. Adiviná cuál.

3. Server Actions: el atajo cuando el formulario es propio

Si el formulario solo lo usa su propia UI, se puede saltear el endpoint HTTP: una Server Action es una función que corre en el servidor y que el formulario llama directo.

"use server"; export async function crearTurnoAction(formData: FormData) { const usuario = await requerirUsuario(); // igual que siempre const resultado = crearTurnoSchema.safeParse({ fecha: formData.get("fecha"), profesionalId: formData.get("profesionalId"), }); if (!resultado.success) { return { error: "Datos inválidos", detalles: resultado.error.flatten() }; } await crearTurno(resultado.data, usuario.id); revalidatePath("/turnos"); // refresca el listado sin recargar la página }

Ojo: una Server Action es un endpoint público con otra cara. Que se llame "como una función" no la exime de validar y autorizar. Ese es el error más frecuente cuando se adoptan.

Usen Route Handler cuando…Usen Server Action cuando…
Lo consume alguien más que su UI (móvil, webhook, Postman) Es su propio formulario y nadie más lo llama
Necesitan controlar status codes y headers Quieren menos código intermedio
Lo van a defender en el parcial con Postman Quieren revalidar la vista sin manejar el refresco a mano

4. Optimistic UI: cuándo sí y cuándo no

Actualizar la pantalla antes de que el servidor confirme hace que la app se sienta instantánea. También hace que mienta, si después falla.

Sí

  • Acciones que casi nunca fallan (marcar favorito, tachar un pendiente)
  • Fáciles de revertir visualmente
  • De bajo costo si salen mal

No

  • Pagos, reservas, cualquier cosa con dinero
  • Acciones que pueden fallar por una regla de negocio (superposición, stock)
  • Todo lo irreversible

5. Qué le pedimos a la IA (y qué no)

Lo que la IA se olvida en los formularios

Genera el camino feliz perfecto y omite los bordes: el doble submit, el error del servidor, los datos que se pierden, el label asociado, el foco en el primer campo con error. Revisen esos cinco en cada formulario generado.

Buen prompt: "Formulario de alta de turno con react-hook-form y zodResolver, usando crearTurnoSchema. Botón deshabilitado mientras envía, error del servidor mostrado sin perder los datos del formulario, labels asociados a cada input, y foco en el primer campo con error."
