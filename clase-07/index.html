Servicios externos: consumir e integrar

Objetivo

Conectar el sistema con algo que no controlan, y —sobre todo— que siga funcionando cuando eso que no controlan falle. Es el último requisito del núcleo obligatorio.

  • 5 min Standup
  • 5 min Metodología: SOA — arquitectura orientada a servicios
  • 25 min Tipos de integración · secretos · fallas · webhooks
  • 15 min Demo: una integración end-to-end y su plan B
  • 50 min Taller: la integración del proyecto
  • 15 min Code review del equipo
  • 5 min Cierre
Esto que leyeron, hoy lo hacen así

La lectura es sobre SOA: servicios que se comparten, interoperabilidad, proveedor y consumidor. Hoy el sistema pasa a ser las dos cosas: consume un servicio de un tercero y expone el suyo. Documentás esa dependencia como lo que es —un proveedor— con sus límites, su plan de contingencia y su contrato.

1. Opciones y qué exige cada una

IntegraciónSirve paraLo difícil
Storage (Vercel Blob, Supabase Storage, S3) Fotos de productos, comprobantes, documentos Límite de tamaño, tipos permitidos, URLs públicas vs. privadas
Email (Resend, SendGrid) Confirmaciones, recordatorios, recupero de clave Que no caiga en spam; nunca bloquear la operación esperando el envío
Pagos (Mercado Pago, Stripe) Cobrar de verdad Webhooks, idempotencia, estados intermedios. El más complejo
Mapas (Google Maps, Mapbox) Direcciones, distancias, geolocalización Costo por request, claves restringidas por dominio
IA en el producto (Claude, OpenAI) Resumir, clasificar, redactar, buscar en lenguaje natural Latencia, costo por token, respuestas no deterministas
Cómo elegir

La que el sistema necesita, no la más impresionante. Si su turnero necesita mandar recordatorios, es email. Meter IA porque queda bien en la presentación, cuando no resuelve nada del dominio, baja la nota en vez de subirla.

2. Todo lo externo falla. Siempre.

El proveedor se cae, el request tarda 30 segundos, se pasaron del límite gratuito, o simplemente no hay internet. Un sistema serio contempla eso antes de que pase.

Frágil

await enviarEmail(...); await crearTurno(...); // Si el email falla, // el turno nunca se crea.

Una funcionalidad secundaria bloquea la principal.

Resistente

const turno = await crearTurno(...); try { await enviarEmail(...); } catch (error) { logger.error("Email falló", error); // El turno YA está creado. // El email se reintenta después. } return turno;

Las cuatro preguntas de toda integración

  1. ¿Es crítica o secundaria? Si es secundaria, nunca puede bloquear el flujo principal.
  2. ¿Qué ve el usuario si falla? "No pudimos enviar el mail de confirmación, pero su turno quedó reservado" es infinitamente mejor que una pantalla de error.
  3. ¿Se puede reintentar sin duplicar? Mandar dos emails molesta; cobrar dos veces es un problema serio. Eso es idempotencia.
  4. ¿Cuánto cuesta cuando crezcan? Busquen los límites del plan gratuito hoy, no cuando lleguen.

3. Secretos y webhooks

Secretos

  • Las claves van en variables de entorno, cargadas en Vercel. Nunca en el código, nunca en el repo.
  • Ninguna clave lleva el prefijo NEXT_PUBLIC_: todo lo que lo lleva termina visible en el navegador.
  • Las llamadas al proveedor se hacen desde el servidor. Si el navegador llama a la API del proveedor, la clave viaja al navegador.
  • Si una clave se filtró alguna vez, se rota. No se "borra el commit".

Webhooks: cuando el proveedor llama al sistema

El sistema ──► "cobrale a este usuario" ──► Mercado Pago │ (el usuario paga, pasan minutos) │ ▼ El sistema ◄── POST /api/webhooks/pagos ◄── Mercado Pago "el pago 123 se aprobó"

Un endpoint de webhook es público: cualquiera en internet puede llamarlo. Por eso:

  • Verifiquen la firma del proveedor. Sin eso, cualquiera puede avisar que "pagó".
  • Hacelo idempotente: los proveedores reenvían el mismo evento si no responden rápido.
  • Respondé 200 enseguida y hacé el trabajo pesado después.

4. Qué le pedimos a la IA (y qué no)

El riesgo específico de esta clase

Las APIs de terceros cambian, y los asistentes recuerdan versiones viejas: nombres de métodos que ya no existen, parámetros renombrados, SDKs reemplazados. Si el código no funciona y "debería", abran la documentación oficial antes de seguir pidiéndole variantes.

Deleguen

  • El cliente del SDK y el manejo de errores
  • Los tipos de la respuesta del proveedor
  • La UI de subida de archivos con su progreso
  • Los reintentos con backoff

Decidan ustedes

  • Si la integración es crítica o secundaria
  • Qué ve el usuario cuando falla
  • Dónde viven los secretos
  • Qué se guarda en su base de la respuesta del proveedor

Y siempre: validen con Zod la respuesta del proveedor. Es una entrada externa como cualquier otra, aunque venga de una empresa grande.

5. Taller

  1. Configurar la cuenta del proveedor y las variables de entorno, en local y en Vercel.
  2. Implementar la integración end-to-end, con su manejo de errores. Debe funcionar en producción, no solo en local.
  3. Romperla a propósito: poner una clave inválida y verificar qué ve el usuario. Si ve una pantalla de error o un mensaje incomprensible, arreglarlo.
  4. Documentar la dependencia en docs/spec.md: proveedor, para qué, límites del plan gratuito, qué pasa si se cae y plan de contingencia.

Entregable de la clase

  • Integración funcionando en producción.
  • La falla del proveedor está contemplada y el usuario ve un mensaje útil.
  • Si es secundaria, no bloquea el flujo principal.
  • Secretos solo en variables de entorno del servidor; ninguno con NEXT_PUBLIC_.
  • La respuesta del proveedor se valida con Zod.
  • Dependencia documentada con límites y plan de contingencia.
