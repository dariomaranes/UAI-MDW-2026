Testing y calidad

Objetivo

Probar que el sistema hace lo que dicen que hace. Y entender el reparto que define esta clase: la IA escribe los tests, ustedes piensan los casos — porque el caso borde que rompe su negocio no está en ningún dataset.

  • 25 min La pirámide de tests · qué testear cuando el tiempo es poco · E2E
  • 15 min Demo: un test que atrapa un bug real
  • 50 min Taller: tests del flujo principal
  • 15 min Code review del equipo
  • 5 min Cierre
Esto que leyeron, hoy lo hacen así

La lectura compara dispositivos reales, emuladores y simuladores. La versión web de ese mismo debate es: ¿alcanza con probar en su Chrome de escritorio? No. Hoy el equipo prueba en las tres capas — tests automatizados (el simulador), el preview deployment (el emulador) y un celular real de alguien del equipo. Los tres encuentran cosas distintas.

1. Qué testear cuando el tiempo es poco

En 16 clases no vamos a buscar cobertura del 100%: no tiene sentido y no se sostiene. La pregunta correcta no es "¿cuánto testeo?" sino "¿qué me duele si se rompe en silencio?".

▲ pocos, lentos, caros ╱ ╲ E2E — el flujo principal completo, como usuario ╱───╲ "reservar un turno de punta a punta" ╱ ╲ ╱ INTEG ╲ — el endpoint contra la base real ╱─────────╲ "POST /turnos rechaza superposición" ╱ ╲ ╱ UNITARIOS ╲ — reglas y schemas puros ╱───────────────╲ "el schema rechaza un título vacío" muchos, rápidos, baratos

Sí testear

  • Las reglas de negocio de su spec.md
  • Los casos borde: vacío, límite, duplicado, fecha pasada, simultaneidad
  • La autorización: que el rol equivocado reciba 403
  • Todo lo que ya se rompió una vez
  • El flujo principal, de punta a punta

No testear

  • Que Prisma sepa hacer un create
  • Que React renderice un div
  • Getters, setters y mapeos triviales
  • Código que va a cambiar la semana que viene
  • Los detalles visuales de un componente
La regla del bug

Cada vez que encuentren un bug, primero escriben el test que lo reproduce y recién después lo arreglan. Es la práctica más barata de todas y la que mejor resultado da: garantiza que ese bug no vuelve, y va construyendo una suite de tests que cubre exactamente lo que su sistema tiene de frágil.

2. Tests de punta a punta

Un test E2E maneja un navegador de verdad: hace clic, escribe, espera y verifica. Es el único que prueba que todas las piezas funcionan juntas.

import { test, expect } from "@playwright/test"; test("un usuario puede reservar un turno", async ({ page }) => { await page.goto("/login"); await page.getByLabel("Email").fill("usuario@ejemplo.com"); await page.getByRole("button", { name: "Ingresar" }).click(); await page.getByRole("link", { name: "Nuevo turno" }).click(); await page.getByLabel("Fecha").fill("2026-09-15T10:00"); await page.getByRole("button", { name: "Guardar" }).click(); await expect(page.getByText("Turno confirmado")).toBeVisible(); });

Fíjense cómo busca los elementos: por etiqueta y por rol, no por clase CSS. Eso no es casualidad — un test escrito así solo pasa si la página es accesible. Si el input no tiene su label, el test no lo encuentra. Es la verificación automática de lo que leyeron en la clase 2.

Cuántos E2E

Pocos: son lentos y se rompen por cualquier cambio de UI. Dos o tres bien elegidos alcanzan para este proyecto: el flujo principal completo, un intento de acceso no autorizado y un camino de error.

3. Qué le pedimos a la IA (y qué no)

El reparto que define esta clase

Una IA genera tests con una facilidad asombrosa. El problema es cuáles genera: los tres casos obvios, los que cualquiera hubiera pensado. El cuarto —el que rompe el negocio— sale de conocer el dominio.

Pídanle "escriban el test de este caso: dos usuarios confirman el mismo turno en el mismo segundo", no "escriban tests para este archivo". Lo primero produce un test que vale; lo segundo, veinte tests que pasan siempre y no protegen de nada.

El antipatrón: el test que se acomoda al bug

Si un test falla y le piden a la IA "arréglenlo", hay una probabilidad alta de que modifique el test en vez del código. El test pasa, el bug queda, y ahora además tienen un test que certifica el comportamiento incorrecto. Cuando algo falla, primero preguntá por qué falla.

4. Taller

  1. Instalar Playwright y dejar corriendo el primer test E2E: login + ver el listado.
  2. Test E2E del flujo principal completo del sistema.
  3. Un test de autorización: el rol que no puede hacer algo, recibe 403 aunque llame al endpoint directamente.
  4. Entre los cuatro, escribir tres casos borde del dominio en un papel. Recién ahí pedirle a la IA que los convierta en tests.
  5. Probar la app en el celular real de cada integrante y anotar lo que falle. Cada hallazgo, un issue.

Dejar los tests corriendo en el CI: un test que no corre solo, no existe.

Entregable de la clase

  • Test E2E del flujo principal, pasando.
  • Test de autorización que verifica el 403.
  • Tres tests de casos borde pensados por el equipo, no por la IA.
  • Todos los tests corriendo en el CI, en verde.
  • La app probada en al menos dos celulares reales distintos, con los hallazgos como issues.
