1. Qué problema resuelve TypeScript

JavaScript deja escribir usuario.nomrbe y enterarse en producción. Ese es el problema: los errores aparecen tarde, cuando ya los está viendo un usuario.

Pero el valor real de TypeScript no es cazar errores de tipeo. Es que obliga a decidir. Cuando escriben un tipo están respondiendo preguntas del dominio que de otra forma quedarían implícitas:

type Turno = { id: string; fecha: Date; profesionalId: string; pacienteId: string; estado: "pendiente" | "confirmado" | "cancelado"; notas?: string; // el "?" dice: puede no existir };

Ese bloque contesta, sin decirlo:

  • ¿Un turno puede existir sin profesional? No.
  • ¿Qué estados existen? Exactamente tres, no cualquier string.
  • ¿Las notas son obligatorias? No.

Sin tipos, esas tres decisiones quedan repartidas en el código y cada integrante asume una cosa distinta.

Inferencia: escriban menos, ganá lo mismo

No hace falta anotar todo. TypeScript deduce solo la mayoría de los tipos. La regla práctica del equipo:

Anoten

  • Los parámetros de las funciones
  • Lo que devuelve una función pública
  • Los tipos del dominio

No anotes

  • Variables locales obvias
  • Resultados de .map(), .filter()
  • Lo que ya está inferido correctamente
El any es contagioso

Un any no apaga el chequeo en una línea: lo apaga en todo lo que toque esa variable. Si no saben el tipo, usen unknown y validen. En este proyecto any está prohibido por el linter.

2. El límite de TypeScript y por qué existe Zod

TypeScript desaparece al compilar. En tiempo de ejecución no queda nada de él. Entonces esto compila perfecto y explota igual:

const datos: Turno = await respuesta.json(); // TypeScript confía. Pero el servidor puede haber devuelto cualquier cosa: // un error, un HTML, un objeto con otra forma.

Regla: todo lo que entra desde afuera del sistema no tiene tipo, tiene una promesa de tipo. Y las promesas de afuera se verifican.

FRONTERAS DEL SISTEMA — acá se valida siempre formulario ──┐ body HTTP ───┤ query params ┼──► [ schema de Zod ] ──► dato tipado y confiable API externa ─┤ variables env┘

Zod resuelve las dos cosas de una sola vez: valida en runtime y genera el tipo.

import { z } from "zod"; export const crearTurnoSchema = z.object({ fecha: z.coerce.date(), profesionalId: z.string().min(1), pacienteId: z.string().min(1), notas: z.string().max(500).optional(), }); // El tipo se DERIVA del schema: nunca pueden quedar desincronizados. export type CrearTurnoInput = z.infer<typeof crearTurnoSchema>;

Ese mismo schema se usa en el formulario (clase 11) y en el endpoint (clase 4). Una sola definición de "qué es un turno válido" en todo el sistema.

3. Decisiones y trade-offs

DecisiónA favorEn contraQué hacemos
type vs interface interface se extiende mejor en jerarquías type es más flexible (uniones, utilitarios) type por defecto; es lo que necesitamos el 95% del tiempo
Validar en todos lados vs. solo en las fronteras Validar todo parece más seguro Duplica reglas y ensucia el código interno Solo en las fronteras. Adentro se confía en el tipo
Tipos del dominio compartidos vs. por capa Compartidos: una sola verdad Acoplan el front al modelo de la base Compartidos al principio; se separan si empiezan a estorbar

4. Qué le pedimos a la IA (y qué no)

El descubrimiento de esta clase

Los tipos son la mejor especificación que le pueden dar a una IA. Un asistente al que le pasan CrearTurnoInput y el schema de Zod escribe código correcto. El mismo asistente, sin tipos, inventa nombres de campos y devuelve algo plausible que no encaja con nada.

Deleguen

  • Escribir el schema de Zod a partir de la descripción del dominio
  • Convertir un JSON de ejemplo en un tipo
  • Refactors mecánicos de tipos
  • Explicarte un error de tipos incomprensible

Decidan ustedes

  • Qué campos son obligatorios y cuáles no
  • Qué estados existen en su dominio
  • Los límites (¿el título puede tener 500 caracteres?)
  • Qué es una entidad y qué es un atributo

Antipatrón frecuente: pedirle a la IA "arreglá este error de tipos". Suele "arreglarlo" con un any o un as, que apaga la alarma sin apagar el incendio. Pídanle que explique el error primero.

5. Taller

Parte 1 — La spec

Completar docs/spec.md del repositorio del equipo:

  1. Problema, para quién y qué mejora.
  2. Los 2 roles y qué puede hacer cada uno que el otro no.
  3. Las entidades: los sustantivos que aparecen cuando describen el sistema.
  4. Al menos 4 historias de usuario con su criterio de aceptación.
  5. Las reglas de negocio que la IA no puede adivinar.
  6. Qué queda fuera de alcance.
Prueba de que la spec sirve

Pasale la spec a un asistente y pídanle que enumere las entidades y sus relaciones. Si lo que devuelve no coincide con lo que tenían en la cabeza, la spec es ambigua: arreglala ahora, que es gratis. Dentro de tres clases, no.

Parte 2 — Los tipos

  • Crear un schema de Zod por entidad en lib/schemas/.
  • Derivar los tipos con z.infer. No escribir el tipo a mano.
  • Usar uniones literales para los estados ("pendiente" | "confirmado"), nunca string pelado.
  • Poner límites explícitos en los strings: mínimos, máximos, formato.
  • Abrir el PR completando la línea de curaduría de la plantilla.

Entregable de la clase

  • docs/spec.md completo y mergeado en main.
  • Un schema de Zod por entidad, con sus tipos derivados.
  • Cero any en el proyecto (npm run typecheck y npm run lint en verde).
  • PR revisado y aprobado por un integrante que no lo escribió.

Para la próxima

  • Lectura del eje metodológico + entrega del cuestionario.
  • Traer dibujadas las entidades y sus relaciones. En papel sirve.
