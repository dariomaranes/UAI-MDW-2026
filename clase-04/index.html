1. De la spec a la API

La clase pasada terminó con las tablas migradas en la nube. Eso es lo que el sistema sabe. Hoy escribimos lo que el sistema hace: la lista de operaciones que ofrece, quién puede pedir cada una y qué contesta en cada caso.

Y sale del mismo lugar que todo lo demás: de docs/spec.md. Trajeron identificadas las operaciones —qué se crea, qué se lee, qué se modifica y qué se borra, y quién puede hacer cada cosa— porque eso, literalmente, es la API. Hoy se le pone método, ruta y código de respuesta.

La traducción, pieza por pieza

Las primeras seis salen casi solas. La séptima es la que hace la diferencia: el núcleo obligatorio pide un flujo de negocio real, no un conjunto de ABMs, y ese flujo siempre tiene una operación que no es crear, leer, modificar ni borrar. Emitir, aprobar, reservar, publicar, facturar, asignar.

Si al terminar el taller su API tiene solamente los cuatro verbos por cada entidad, todavía no modelaron el negocio: modelaron una planilla de cálculo con botones. Búsquenla ahora, que es la que se defiende en el Parcial I.

Por qué se hace ahora y por qué se hace sin pantallas

Porque la API es la parte del sistema que sobrevive a todo lo demás. La pantalla se rediseña tres veces, el framework de UI se cambia, el celular reemplaza a la web — y las operaciones siguen siendo las mismas. Por eso se piensa primero, y por eso el Parcial I de la clase 9 es una defensa del backend: se prueba con la API, no con botones.

Y hay una razón práctica: una API se puede probar sola. Hoy van a verificar cada operación con un archivo de pruebas, sin depender de que alguien haya hecho un formulario. Cuando en la clase 10 aparezca la UI, va a consumir algo que ya funciona.

2. Metodología: Scrum

Scrum es el marco de trabajo ágil más usado del mundo, y también el peor entendido. La confusión más común es creer que es una metodología de desarrollo. No lo es: Scrum no dice absolutamente nada sobre cómo escribir una línea de código. Dice cómo se organiza un equipo para entregar algo cada tanto tiempo, sin decidir por él qué hace adentro.

Las tres piezas: quién, qué y cuándo

Scrum tiene tres tipos de pieza y no hay un cuarto: los roles (quién), los artefactos (qué) y los eventos (cuándo). Todo lo que el marco define entra en alguna de las tres. Acá va una fila por pieza, agrupada por tipo — de los eventos están los que tienen equivalente en la cursada: el daily scrum, con una clase por semana, no se puede replicar y no hay que inventarlo.

3. Qué es REST

Una API es la puerta del sistema para otro programa: lo mismo que una pantalla es para una persona. REST es un estilo para diseñar esa puerta usando lo que HTTP ya trae: direcciones, verbos y códigos de respuesta. No es una librería ni algo que se instale — es una forma de ponerle nombre a las cosas.

Lo que sigue es REST pragmático, que es lo que se usa en la industria: recursos en la URL, verbos HTTP, JSON y status codes.

Y una palabra que van a leer todo el día, así que conviene fijarla ahora: cada una de esas direcciones —POST /api/mascotas— es un endpoint, un punto de entrada al sistema. La API es el conjunto de todos. El endpoint es dónde se toca; lo que atiende del otro lado tiene otro nombre en cada framework, y el de Next lo vemos en la sección 4.

La idea central: sustantivos en la URL, verbos en el método

La URL nombra una cosa, no una acción. Qué se hace con esa cosa lo dice el método HTTP, que ya existe y que ya conoce todo el mundo — navegadores, proxies, caches y la persona que va a leer sus logs.

Así no

POST /api/crearMascota GET /api/getMascotas POST /api/mascota/borrar/12 POST /api/actualizarMascota

El verbo está dos veces: en el método y en la URL, a veces contradiciéndose (POST para borrar). Cada operación nueva inventa una convención nueva, y a la décima nadie recuerda si era getX, listX o obtenerX.

Así sí

POST /api/mascotas GET /api/mascotas DELETE /api/mascotas/12 PATCH /api/mascotas/12

Una sola dirección para el recurso "mascotas" y otra para "una mascota". Quien conoce un recurso ya sabe usar todos los demás, que es todo el punto de tener una convención.

Los verbos, y la palabra que se pregunta en el parcial

MétodoPara qué¿Cambia datos?¿Idempotente?
GET Leer. Nunca modifica nada No Sí
POST Crear un recurso nuevo, o disparar una operación Sí No
PUT Reemplazar un recurso entero Sí Sí
PATCH Modificar algunos campos Sí Depende de lo que haga
DELETE Borrar Sí Sí

Idempotente significa que hacer la misma llamada dos veces deja el sistema igual que hacerla una. No es teoría: es lo que pasa cuando alguien hace doble clic en el botón, o cuando se corta el wifi y el celular reintenta.

DELETE /api/mascotas/12 ×2 → la mascota 12 no existe. Igual que ×1. PATCH /api/mascotas/12 ×2 → el mismo nombre puesto dos veces. Igual. POST /api/mascotas ×2 → DOS mascotas. NO es lo mismo. Por eso el único método peligroso ante un reintento es POST, y por eso las operaciones que crean cosas necesitan cuidado.

Los status codes que van a usar

El status es la primera respuesta que da el endpoint, antes del cuerpo. Un cliente tiene que poder decidir qué hacer mirando solo ese número.

CódigoSignificaCuándo lo devuelven
200 OKSalió bienUn GET, un PATCH, un DELETE que respondió
201 CreatedSe creó un recursoUn POST que crea. Se devuelve el objeto creado, con su id
204 No ContentSalió bien y no hay nada que devolverUn DELETE. La respuesta viene vacía a propósito: no es un error
400 Bad RequestEl cliente mandó algo malCuando Zod rechaza el body. El más frecuente de todos
401 UnauthorizedNo sé quién sosNo hay sesión. Es no autenticado, aunque el nombre diga otra cosa
403 ForbiddenSé quién sos y no podésUn dueño intentando emitir un certificado
404 Not FoundNo existeUn id que no está… y también un recurso que existe pero no es suyo (ver sección 8)
409 ConflictExiste pero choca con el estado actualEmitir un certificado ya emitido; un email repetido
500 Server ErrorSe rompió del lado del servidorNunca a propósito. Un 500 es siempre un bug suyo
El antipatrón más común: el 200 que miente

Es tentador devolver siempre 200 con un { ok: false, mensaje: "..." } adentro. Funciona… hasta que algo lo consume automáticamente: el fetch del navegador no falla, el monitoreo no ve ningún error, la pantalla muestra un cartel de éxito y el registro nunca se guardó.

El status es parte de la respuesta, no un detalle. Si algo salió mal, el número tiene que decirlo.

La operación que no es un CRUD: emitir

Emitir no es "actualizar el estado del certificado". Es un acto con sus propias reglas: verifica que las vacunas obligatorias sigan al día, genera un código único, congela la fecha de vencimiento y guarda quién lo emitió. Hay dos formas de escribirlo y la diferencia importa:

✗ PATCH /api/certificados/12 { "estado": "EMITIDO" } ✓ POST /api/certificados/12/emision

Con el PATCH, es el cliente el que decide la transición y el servidor obedece: nada impide mandar { "estado": "ANULADO" } o saltarse un paso. Con el sub-recurso, el cliente pide que ocurra la operación y el servidor decide si corresponde. Además cada transición tiene su propio permiso —emitir y anular no los hace la misma persona— y así queda cada una en su endpoint.

Regla: si una transición de estado tiene reglas o permisos propios, merece su propia ruta.

La URL no es la pantalla

/api/mascotas/12 es el recurso mascota 12. /mascotas/12 —sin api— va a ser la página que la muestra, y la van a escribir en la clase 10. Pueden parecerse o no: una pantalla suele mostrar varios recursos, y un recurso puede no tener pantalla propia.

4. Route Handlers en Next.js

Un Route Handler es un archivo que exporta una función por cada método HTTP que soporta. Next lo publica en la URL que corresponde a su ubicación en el directorio: la ruta es la carpeta.

app/ └─ api/ ├─ mascotas/ │ ├─ route.ts → /api/mascotas │ └─ [id]/ │ ├─ route.ts → /api/mascotas/:id │ └─ aplicaciones/ │ └─ route.ts → /api/mascotas/:id/aplicaciones ├─ aplicaciones/ │ └─ route.ts → /api/aplicaciones └─ certificados/ └─ [id]/ └─ emision/ └─ route.ts → /api/certificados/:id/emision El archivo SIEMPRE se llama route.ts. Los corchetes son la parte variable de la URL.

Anatomía de un endpoint

El template ya trae este archivo como ejemplo, con el patrón comentado. Son cuatro pasos, siempre en el mismo orden:

// app/api/mascotas/route.ts import { NextResponse } from "next/server"; import { crearMascotaSchema } from "@/lib/schemas/mascota"; import { crearMascota, listarMascotasDeDueno } from "@/lib/db/mascotas"; export async function GET() { // TODO (clase 6): el dueño sale de la sesión. const mascotas = await listarMascotasDeDueno(duenoId); return NextResponse.json(mascotas); // 200 por defecto } export async function POST(request: Request) { // 1. VALIDAR. El body puede venir de cualquier lado, no solo del // formulario propio. Nunca se confía. const body: unknown = await request.json(); const resultado = crearMascotaSchema.safeParse(body); if (!resultado.success) { return NextResponse.json( { error: "Datos inválidos", detalles: resultado.error.flatten() }, { status: 400 }, ); } // 2. AUTORIZAR. Quién es sale de la sesión del servidor, NUNCA del body. // TODO (clase 6): usuario real y 401 si no hay sesión. const duenoId = "usuario-de-ejemplo"; // 3. DELEGAR. El handler no habla con Prisma: para eso está lib/db. const mascota = await crearMascota(resultado.data, duenoId); // 4. RESPONDER con el status correcto y el recurso creado. return NextResponse.json(mascota, { status: 201 }); }

Ese orden no es estético: validar antes de autorizar evita gastar una consulta de sesión en un body basura, y autorizar antes de delegar garantiza que ninguna consulta se ejecute a nombre de alguien que no corresponde.

La parte variable de la URL

En una ruta con [id], el valor llega por el segundo parámetro. En Next 15 params es una promesa y hay que esperarla: es el error de compilación más común de esta clase.

// app/api/mascotas/[id]/route.ts export async function GET( _request: Request, { params }: { params: Promise<{ id: string }> }, ) { const { id } = await params; // ← el await no es opcional const mascota = await obtenerMascota(id); // Un id que no existe no es un error del servidor: es un 404. if (!mascota) { return NextResponse.json({ error: "No encontrada" }, { status: 404 }); } return NextResponse.json(mascota); }

Y lo que viene después del ? —filtros, paginación— se lee del request, y se valida igual que el body, porque es igual de público:

const { searchParams } = new URL(request.url); const especie = searchParams.get("especie"); // string | null, SIEMPRE texto
Todo lo que está en app/api/ es internet

En cuanto hagan git push, cada uno de esos archivos es una URL pública que cualquiera puede llamar con un cliente HTTP cualquiera, desde cualquier parte del mundo, sin pasar por su interfaz. Nadie tiene que "hackear" nada: la dirección está a la vista.

De ahí sale la regla que va a gobernar las clases 5 y 6: esconder un botón no es una medida de seguridad. Si un endpoint no valida y no verifica quién llama, no está protegido — está sin usar todavía.

¿Y las páginas no van a usar la API?

En Next las páginas corren en el servidor, así que una página puede llamar a lib/db/ directamente, sin dar la vuelta por HTTP. Es más rápido y es lo que van a hacer en la clase 8 para leer datos.

Entonces, ¿para qué la API? Para todo lo que no es su propia página: el navegador cuando ya está cargado, una app móvil, un sistema que integre con ustedes, Postman — y la defensa del Parcial I, que se toma sobre el backend cuando todavía no hay interfaz. Una operación que solo existe adentro de un componente no se puede probar ni mostrar sola.

5. Server Actions

Una Server Action es una función del servidor que un formulario del navegador puede invocar como si la tuviera al lado. No se escribe endpoint, no se arma el fetch, no se serializa nada: se le pasa la función al form y listo.

Que es imposible, y por eso hay que entender qué pasa realmente. La función vive en el servidor; el formulario, en la máquina del usuario. No se pueden llamar. Lo que hace Next al compilar es otra cosa: deja la función de verdad en el servidor y, en el bundle del navegador, pone en su lugar una función hueca con un ID secreto —un stub, que es como se llama— y publica una URL escondida para invocarla. Cuando el usuario manda el formulario, lo que viaja es un POST por HTTP, igual que siempre. Next escribió el fetch que ustedes no escribieron.

El control remoto

Apretás "volumen +" y sentís que subiste el volumen. Pero el botón no sube nada: manda una señal, y el televisor sube el volumen. El control remoto es el stub, la señal es el POST, el televisor es el servidor.

Y de ahí sale sola la parte incómoda: si hay una señal viajando por el aire, cualquiera con el aparato correcto puede mandarla sin tocar tu control remoto.

Lo que se ahorra con eso es todo el andamiaje de hablar con uno mismo: el onSubmit, el preventDefault, el fetch con su JSON.stringify, el estado de carga y algo que refresque la lista. Seis piezas para llamar a tu propio servidor. Y hay un premio extra: ese formulario funciona incluso con el JavaScript deshabilitado, porque en el fondo es un form de HTML. Cómo se escribe se ve en la clase 11, cuando haya pantallas donde colgarlo.

Una Server Action es un endpoint público con otro nombre

Esta es la confusión más peligrosa de la clase. Como la función se escribe en un archivo del proyecto y se llama como cualquier otra, parece privada. No lo es: al compilar, Next publica una ruta para poder invocarla desde el navegador. Cualquiera puede llamarla con las herramientas de desarrollo abiertas, sin pasar por el formulario.

Consecuencia práctica: una Server Action tiene exactamente las mismas obligaciones que un Route Handler. Valida su entrada y verifica quién llama. Lo único que cambia es cómo se escribe; el riesgo es idéntico.

Qué se resigna

  • No hay status codes. Se devuelve un objeto y quien la llamó lo interpreta. Sirve para su propia interfaz; no sirve como contrato para un tercero.
  • No tiene una URL estable ni documentable. El identificador lo genera el compilador y cambia entre builds. Un cliente externo no puede depender de eso.
  • Es de Next. Un Route Handler es HTTP y lo entiende cualquier cosa; una Server Action solo existe adentro de este framework.

6. Cuándo REST y cuándo Server Action

Los dos hacen lo mismo con el mismo código de negocio detrás. Lo que cambia es quién los llama, y esa es toda la regla de decisión.

Si el que llama es…VaPor qué
Un formulario de su propia app Server Action Es el caso para el que existen: menos código y menos lugares donde equivocarse
Una app móvil, otro sistema, un webhook Route Handler Necesitan una URL estable y HTTP de verdad
Un api.http, Postman, la defensa del Parcial I Route Handler Es lo único que se puede probar sin interfaz
Una página del servidor que solo lee Ninguno: lib/db/ directo Dar la vuelta por HTTP contra uno mismo agrega latencia y no aporta nada
Algo que tiene que ser cacheable o compartible por URL Route Handler (GET) La verificación pública del certificado es el ejemplo perfecto
La regla de la materia, para que no quede a criterio

1. Todo el núcleo del dominio se expone como API REST. No es negociable: el Parcial I de la clase 9 se defiende sin interfaz, y lo que no tenga endpoint no se puede mostrar.

2. Las Server Actions son para las mutaciones que dispara la propia UI. Hoy no escriben ninguna —no hay UI todavía— y se trabajan en serio en la clase 11. Están acá para que sepan qué son antes de que la IA les escriba una, y para que la reconozcan cuando aparezca.

3. Y la que importa: la lógica no vive en ninguno de los dos. Handler y action son cáscaras finas sobre el mismo código. Si mañana hay que cambiar cómo se emite un certificado, se cambia en un solo lugar y las dos puertas se enteran.

7. Las capas: quién puede hablar con quién

Con dos entidades cualquier organización funciona. El problema aparece en la clase 10, cuando hay veinte archivos y una consulta lenta, y la pregunta "¿dónde se lee esto?" no tiene una sola respuesta. Por eso el orden se pone hoy, que es gratis.

navegador · Postman · app móvil │ HTTP ▼ ┌─────────────────────────────────┐ │ app/api/**/route.ts │ la frontera: │ app/**/acciones.ts │ validar · autorizar · responder └───────────────┬─────────────────┘ │ ▲ ▼ │ (una página del servidor entra acá) ┌─────────────────────────────────┐ │ lib/db/*.ts │ las consultas: select, take, include │ lib/*.ts │ las reglas del negocio └───────────────┬─────────────────┘ ▼ ┌─────────────────────────────────┐ │ Prisma → Postgres │ └─────────────────────────────────┘ La flecha nunca salta un nivel, y nunca va para arriba.

Las tres reglas

  1. Ningún route.ts importa Prisma. Si aparece un prisma. adentro de app/, esa consulta ya está en un solo lugar del que nadie más se puede aprovechar, y el día que esté lenta nadie la va a encontrar.
  2. Ninguna función de lib/db/ sabe qué es un request. Recibe datos y devuelve datos. Por eso se puede llamar igual desde un endpoint, desde una Server Action, desde una página o desde un test.
  3. Quién es el usuario se decide en la frontera y baja por parámetro. crearMascota(datos, duenoId): el duenoId lo pone el handler leyendo la sesión, y nunca sale del body.

Dos cosas que se deciden en las consultas de hoy

Devolver la fila entera

return prisma.mascota.findMany({ include: { dueno: true }, });

Ese include devuelve el email de todos los dueños en un endpoint de listado. Nadie lo pidió, la pantalla no lo usa, y está publicado en internet. Es la fuga de datos más común que existe, y no se ve porque la pantalla queda igual.

Elegir columnas

return prisma.mascota.findMany({ where: { duenoId }, take: 50, select: { id: true, nombre: true, especie: true, dueno: { select: { nombre: true } }, }, });

select explícito: sale lo que se decidió que salga. where con el dueño, que es la regla de negocio. Y take, porque todo listado lleva límite: sin él, el día que haya 40.000 filas el endpoint las trae todas.

Y ahí está el N+1 de la clase pasada, ya no como advertencia: ese select anidado es la forma correcta, y la incorrecta —pedir el dueño adentro de un for— se escribe casi igual de natural.

8. Decisiones: qué se gana y qué se resigna

DecisiónA favorEn contraQué hacemos
Un endpoint por recurso vs. uno por pantalla Uno por pantalla trae de una todo lo que esa vista necesita, en una sola llamada Cada cambio de diseño obliga a tocar el backend, y ese endpoint no lo puede reusar nadie más Por recurso. La API sobrevive al rediseño; la pantalla arma lo que precisa
Recurso ajeno: 403 o 404 403 es más honesto: "existe y no podés" Y con eso confirma que el recurso existe, que a veces ya es información de más 403 si el problema es el rol (un dueño emitiendo). 404 si el problema es que no es suyo: la mascota del vecino, para ustedes, no existe
PUT vs. PATCH PUT es idempotente y más simple de razonar Obliga a mandar el objeto completo: un campo que falte se borra PATCH, con crearMascotaSchema.partial(), que ya escribieron en la clase 2
Rutas anidadas vs. planas Anidar se lee como el dominio: /mascotas/12/aplicaciones Anidar de más da rutas larguísimas y duplicadas Un solo nivel de anidamiento, y solo cuando el hijo no tiene sentido sin el padre

9. Qué le pedimos a la IA (y qué no)

Hoy la IA escribe la API entera. Ese es el problema

Con el schema.prisma de la clase pasada, cualquier asistente genera los cinco endpoints de las seis entidades en un minuto, y todo compila. Lo que no puede saber es quién puede llamar a cada uno, qué campos se pueden devolver y cuál de esas operaciones es en realidad el negocio — que son las tres cosas que se evalúan.

El síntoma es fácil de reconocer: una API generada tiene treinta endpoints perfectamente simétricos y ninguno se llama "emitir".

Deleguen

  • El esqueleto del handler una vez que le dieron el contrato
  • Las consultas de lib/db/ con su select
  • El api.http, con los tres casos de cada endpoint
  • Revisar su tabla de rutas y decirles cuál falta o cuál se solapa
  • Explicarles un error de tipos de params

Decidan ustedes

  • Qué recursos existen y cómo se llaman
  • Qué rol puede llamar a cada operación
  • Qué status devuelve cada error
  • Qué campos salen y cuáles no
  • Cuál es la operación del flujo principal
El antipatrón de esta clase: el data: body

Es la línea que sale sola, y es la vulnerabilidad más clásica que existe:

// ✗ lo que escribe un asistente sin contexto export async function POST(request: Request) { const body = await request.json(); const mascota = await prisma.mascota.create({ data: body }); return NextResponse.json(mascota); }

Anda perfecto con el formulario propio. Ahora miren qué pasa si alguien manda { "nombre": "Fido", "duenoId": "el-id-del-vecino" } desde Postman: el sistema le crea una mascota a otra persona. Nadie rompió nada — el endpoint hizo exactamente lo que le pidieron.

Y en cuanto el modelo crezca es peor: cualquier columna que exista pasa a ser escribible desde afuera. Un campo rol en Usuario con esta línea significa que cualquiera puede registrarse como veterinario, que es literalmente la regla de negocio que la spec declara crítica.

Las dos correcciones son las mismas de siempre: el body pasa por Zod —que descarta lo que no está en el schema— y la identidad no se lee del body, baja de la sesión.

10. Taller

Tres fases, en este orden. La primera es en papel otra vez, y por la misma razón que la clase pasada: escribir un handler lleva cinco minutos; decidir qué operaciones existen y quién puede llamarlas, no. El editor se abre en la fase B.

A. EL CONTRATO papel y docs/api.md, editor cerrado B. LOS ENDPOINTS app/api/ + lib/db/, la lógica en un solo lugar C. LA PRUEBA sin interfaz: docs/api.http, local y producción

Fase A — El contrato, con el editor cerrado

Con docs/spec.md abierto y la lista de operaciones que trajeron. Todo esto se contesta entre los cuatro, en voz alta.

  1. Una fila por operación. Recorran las historias de usuario y, por cada una, escriban qué se crea, qué se lee, qué se modifica y qué se borra. Si una historia no genera ninguna operación, o está mal escrita o no era una historia.
  2. Pónganle método y ruta a cada fila. Sustantivo en plural en la URL, verbo en el método. Si les sale un verbo en la URL, es que la operación no es un CRUD: va al punto 4.
  3. La columna del rol. Quién puede llamar a esa operación, según la tabla de roles de su spec. Ninguna fila puede quedar vacía, y las que digan "cualquiera" tienen que ser públicas a propósito, como la verificación del certificado.
  4. Busquen la operación que no es un ABM. Está en el paso 4 o 5 de su flujo principal, y es la que decide si esto es un producto o una planilla. Decidan su ruta: POST /api/<recurso>/:id/<la-operación>. Fíjense que el verbo se convierte en sustantivo — es lo que lo mantiene REST:
    emitir → POST /api/certificados/:id/emision confirmar → POST /api/reservas/:id/confirmacion aprobar → POST /api/solicitudes/:id/aprobacion publicar → POST /api/articulos/:id/publicacion asignar → POST /api/tickets/:id/asignacion cancelar → POST /api/turnos/:id/cancelacion despachar → POST /api/pedidos/:id/despacho inscribir → POST /api/cursos/:id/inscripciones
    La última es la excepción que confirma la regla: si la operación puede ocurrir muchas veces sobre el mismo recurso, el sustantivo va en plural y es una colección de verdad. Emitir un certificado pasa una vez; inscribirse a un curso, muchas.
  5. Los casos de error, con su status. Ya están escritos en los criterios de aceptación de cada historia —"caso de error: si…"—: hoy se convierten en un número. Este es el insumo de la clase 5, así que cuanto más completo, mejor.
  6. Vuélquenlo a docs/api.md con esas cuatro columnas. Es un archivo nuevo y es parte del entregable:
    | Método y ruta | Qué hace | Rol | Errores | |------------------------------------|--------------------------|-------------|----------| | POST /api/certificados | Solicitar un certificado | Dueño | 400, 409 | | POST /api/certificados/:id/emision | Emitirlo | Veterinario | 403, 404 |

Fase B — Los endpoints

  1. Un archivo por recurso. app/api/<recurso>/route.ts para la colección (GET y POST) y app/api/<recurso>/[id]/route.ts para el individual (GET, PATCH, DELETE). Recuerden el await params.
  2. Los cuatro pasos, en orden, en todos. Validar con el schema de Zod que ya tienen, autorizar, delegar, responder. Donde todavía no hay sesión va el TODO (clase 6) explícito, como en el archivo de ejemplo del template: un TODO escrito es una decisión postergada; un TODO ausente es una que nadie tomó.
  3. Las consultas, en lib/db/<entidad>.ts. Con select explícito y take en todo listado. Chequeo rápido: grep -r "prisma\." app/ no tiene que devolver nada.
  4. El mínimo que hay que tener funcionando:
    [ ] CRUD completo de la entidad principal del dominio [ ] El listado que filtra por dueño (o el equivalente de su spec) [ ] La operación del flujo principal, la que no es un ABM [ ] Un GET público, si su dominio tiene alguno
  5. npm run typecheck y npm run lint en verde antes de abrir el PR.
Deléguenlo, pero después de la fase A

Los handlers sí son buenos candidatos a delegar: son repetitivos y las decisiones ya las tomaron ustedes en el papel. Toda la diferencia está en cuánto contexto le dan:

✗ "Hacéme la API REST de este schema.prisma" ✓ "Escribí app/api/certificados/route.ts siguiendo el patrón de app/api/mascotas/route.ts: GET lista los certificados de las mascotas del dueño de la sesión con listarCertificadosDeDueno, POST valida con solicitarCertificadoSchema (400 si falla), el duenoId sale de la sesión y NO del body, delega en solicitarCertificado y devuelve 201. Dejá el TODO de la clase 6 donde va la sesión. No importes prisma en este archivo."

En el segundo caso hace tipeo. En el primero toma todas las decisiones de la fase A —y las toma bien parecido para los seis recursos, que es justo lo que oculta que las tomó alguien más.

Fase C — Probarla sin interfaz

No hay pantallas todavía y no hacen falta. La API se prueba con un archivo docs/api.http, que se corre desde el editor con la extensión REST Client. Es parte del entregable: queda versionado, se revisa en el PR igual que cualquier otro archivo, y es lo que van a abrir en la defensa del Parcial I.

### docs/api.http @base = http://localhost:3000 # @base = https://<la-url-que-les-dio-vercel> ### crear → tiene que devolver 201 y el objeto con su id POST {{base}}/api/mascotas Content-Type: application/json { "nombre": "Fido", "especie": "PERRO", "fechaNacimiento": "2024-03-01" } ### el mismo con un dato inválido → tiene que devolver 400, NO 500 POST {{base}}/api/mascotas Content-Type: application/json { "nombre": "", "especie": "DRAGON" } ### un id que no existe → 404 GET {{base}}/api/mascotas/no-existe ### listar GET {{base}}/api/mascotas

Arriba de cada ### aparece un Send Request: click, y la respuesta se abre al costado con el status y los headers a la vista. Para probar contra producción se descomenta la segunda línea y se vuelve a correr el archivo entero, sin tocar nada más.

Postman, y por qué no es el entregable

En la demo van a ver el mismo endpoint una vez en Postman: es lo que se van a encontrar en cualquier equipo, y muestra la respuesta más grande y más cómoda de leer. Si les resulta más claro para trabajar, úsenlo.

Lo que se entrega igual es el api.http, por una razón sola: vive en el repo. Una colección de Postman está en la cuenta de quien la armó, hay que exportarla para compartirla, y se desactualiza el día que alguien cambia una ruta sin que el resto se entere. El archivo del repo se revisa en el mismo PR que el endpoint que prueba, y llega a la defensa junto con el código.

  1. Prueben los tres casos de cada endpoint: el que anda, el body inválido y el recurso que no existe. Los tres van al api.http, no solo el que anda. Y miren el status, no el body: un 500 donde tenía que haber un 400 es el error más común de hoy, y desde afuera los dos se ven igual de "roto".
  2. Repitan las mismas pruebas contra producción después del merge: descomenten la línea de @base con la URL de Vercel y corran el archivo entero otra vez. Ese es el hito: un endpoint que anda en localhost y no en la URL pública, para esta materia, no existe. Si falla solo en producción, casi siempre es una variable de entorno que está en el .env.local y no en el panel de Vercel.
  3. PR y code review. Además de lo de siempre, el que revisa mira estas seis cosas:
    [ ] ¿Hay algún `prisma.` adentro de app/ ? [ ] ¿Algún endpoint hace `data: body` sin pasar por Zod? [ ] ¿Alguna identidad (duenoId, emisorId, autorId) sale del body? [ ] ¿Algún listado sin `take` o sin `select`? [ ] ¿Las rutas coinciden con docs/api.md? [ ] ¿docs/api.http tiene los tres casos de cada endpoint nuevo?
Ojo con probar POST contra la base compartida

Su .env.local apunta a la misma base de Supabase que usan los cuatro y que usa producción. Cada POST de prueba deja una fila real, y a las dos horas de taller la tabla tiene treinta mascotas llamadas "asdasd".

No es grave hoy, pero sí antes del parcial: usen nombres reconocibles (PRUEBA-nombre), y dejen la base limpia con npm run db:seed antes de la demo. El seed es idempotente justamente para eso.

Si el equipo no usa Next

Las Server Actions no existen fuera de Next y no hay que reemplazarlas: es una característica del framework, no un requisito. Lo que sí se exige igual es la API REST completa con su docs/api.md, la separación entre la capa que atiende el request y la que consulta la base, y que todo responda en la URL pública. En Express, Fastify o Django el patrón de cuatro pasos es exactamente el mismo; cambian los nombres.
