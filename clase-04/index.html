1. HTTP: lo mínimo que no se negocia

Una API es un contrato. El cliente pide algo y el servidor responde diciendo qué pasó. El status code no es decoración: es la mitad de la respuesta.

VerboQué significaÉxitoError típico
GETTraer datos, sin efectos200404 si no existe
POSTCrear un recurso nuevo201400 si los datos son inválidos
PATCHModificar parte de un recurso200404 / 400
PUTReemplazar el recurso completo200404 / 400
DELETEEliminar204 (sin cuerpo)404

Los status codes que van a usar

CódigoSignificaCuándo
200 / 201 / 204Salió bienLeer / crear / borrar
400El cliente mandó algo malFalló la validación de Zod
401No sé quién sonNo hay sesión
403Sé quién son y no puedenRol equivocado
404No existeEl id no está en la base
409Conflicto con el estado actualTurno superpuesto, email repetido
500Se rompió el servidorBug propio. Nunca es culpa del cliente
El error más común de esta clase

Responder 200 con { error: "..." } adentro. El cliente ve un 200, asume éxito, y el bug aparece tres pantallas después. 401 y 403 no son lo mismo, y confundirlos hace imposible depurar.

2. Route Handlers vs. Server Actions

Next.js les da dos formas de correr código en el servidor. No compiten: resuelven cosas distintas.

Route Handler — app/api/…/route.ts

Un endpoint HTTP de verdad, con URL propia.

Usalo cuando:

  • Lo consume alguien más que su propia UI (una app móvil, un webhook, Postman)
  • Necesitan controlar el status code y los headers
  • Quieren poder probarlo sin abrir el navegador

Server Action — "use server"

Una función del servidor que el cliente llama como si fuera local.

Usalo cuando:

  • Es una mutación que dispara su propio formulario
  • No necesitan un endpoint público
  • Quieren menos código intermedio (clase 11)
Regla del cuatrimestre

El Parcial I se defiende con Postman, así que el CRUD principal va como Route Handlers. En la clase 11, cuando lleguen los formularios, se agregan Server Actions donde tengan sentido. Ambas cosas conviven en el mismo proyecto.

La forma de un endpoint en este proyecto

export async function POST(request: Request) { // 1. VALIDAR: el body puede venir de cualquier lado, no solo de su form const body: unknown = await request.json(); const resultado = crearTurnoSchema.safeParse(body); if (!resultado.success) { return NextResponse.json( { error: "Datos inválidos", detalles: resultado.error.flatten() }, { status: 400 } ); } // 2. AUTORIZAR: quién son sale de la sesión, nunca del body (clase 6) const usuario = await requerirUsuario(); // 3. DELEGAR: el acceso a datos vive en lib/db/, no acá const turno = await crearTurno(resultado.data, usuario.id); // 4. RESPONDER con el código correcto return NextResponse.json(turno, { status: 201 }); }

Las cuatro etapas, siempre en ese orden, en todos los endpoints del proyecto. Un endpoint que no las tenga es un endpoint que la revisión rechaza.

3. Demo: generar un CRUD y revisarlo

Hoy el CRUD lo escribe la IA en un minuto. Lo que se practica es la revisión. Estos son los seis errores que aparecen una y otra vez en código generado; buscalos en el diff antes de aprobar:

#Qué buscarPor qué importa
1El body se usa sin validarCualquiera manda cualquier cosa
2El userId se lee del bodyMe hago pasar por otro cambiando un campo
3Todo responde 200El cliente no puede distinguir éxito de error
4Prisma importado directo en route.tsRompe la regla del AGENTS.md: el acceso a datos va en lib/db/
5findMany sin takeCon 50.000 registros, el endpoint se cae
6El error de la base se devuelve tal cualFiltra la estructura interna al atacante
Cómo pedirlo bien

Un prompt que evita la mitad de estos errores: "Implementen el CRUD de Turno siguiendo AGENTS.md. Validen con crearTurnoSchema. El acceso a datos va en lib/db/turnos.ts. Devolvé 201 al crear, 400 si la validación falla y 404 si no existe. No importes Prisma en el route handler."

Fíjense lo que pasó: para escribir ese prompt tuvieron que saber todo lo de esta clase. Prompting no es un atajo al conocimiento, es una forma de aplicarlo.

4. Taller

  1. Armar el tablero del equipo: las historias de la spec convertidas en issues, con responsable.
  2. CRUD completo de la entidad principal en app/api/<recurso>/:
    • GET /api/<recurso> — listar, con límite
    • POST /api/<recurso> — crear, 201
    • GET /api/<recurso>/[id] — detalle, 404 si no existe
    • PATCH /api/<recurso>/[id] — modificar
    • DELETE /api/<recurso>/[id] — eliminar, 204
  3. Colección de Postman con los 5 endpoints, incluyendo un request que falle a propósito (body inválido) para verificar el 400. Exportarla a docs/postman/.
  4. Code review del diff usando la tabla de los 6 errores. Revisa el PR alguien del equipo que no lo escribió, y deja al menos 2 comentarios.

Entregable de la clase

  • Los 5 endpoints funcionando contra la base real.
  • Validación con Zod en todo lo que recibe datos.
  • Status codes correctos, incluido el 404 y el 400.
  • Prisma no aparece importado fuera de lib/db/.
  • Colección de Postman exportada en el repo.
  • Tablero del equipo con las historias como issues.
  • PR revisado por un integrante que no lo escribió, con al menos 2 comentarios.
