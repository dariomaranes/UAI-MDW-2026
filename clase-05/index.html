Validación, manejo de errores y capas

Objetivo

Que el sistema falle bien. Que valide donde corresponde, que le diga al usuario algo útil cuando algo sale mal, y que no filtre información interna cuando se rompe.

  • 5 min Standup
  • 5 min Metodología: Ágil — manifiesto, Scrum y Kanban
  • 25 min Capas · dónde valida cada una · errores del dominio
  • 15 min Demo: un error de negocio de punta a punta
  • 50 min Taller: validaciones, errores tipados y primeros tests
  • 15 min Code review del equipo
  • 5 min Cierre
Esto que leyeron, hoy lo hacen así

La lectura es sobre Ágil. De todo el manifiesto, hoy se aterriza una sola cosa: el equipo escribe su Definition of Done en el README. Qué significa exactamente que una tarea está terminada en este proyecto. Sin eso, "ágil" es una excusa para entregar cualquier cosa rápido.

1. Las capas y quién valida qué

┌──────────────────────────────────────────────────────────┐ │ CLIENTE valida para AYUDAR al usuario │ │ (feedback inmediato, no bloquea a nadie) │ └──────────────────────────────────────────────────────────┘ ↓ no es confiable ┌──────────────────────────────────────────────────────────┐ │ API valida para PROTEGER el sistema │ │ forma de los datos + permisos │ └──────────────────────────────────────────────────────────┘ ↓ ┌──────────────────────────────────────────────────────────┐ │ DOMINIO valida las REGLAS DE NEGOCIO │ │ lib/db/ "no puede superponerse", "no cancelar │ │ un turno que ya pasó" │ └──────────────────────────────────────────────────────────┘ ↓ ┌──────────────────────────────────────────────────────────┐ │ BASE DE DATOS garantiza lo INVIOLABLE │ │ @@unique, foreign keys, not null │ └──────────────────────────────────────────────────────────┘

Las cuatro validan, pero por razones distintas. La del cliente se puede saltear con Postman. La de la base es la única que ningún bug puede evitar.

La frase que hay que grabarse

El cliente nunca es confiable. No porque sus usuarios sean malos, sino porque el navegador es una computadora ajena. Cualquiera puede abrir las DevTools, o directamente mandar el request a mano.

2. Tres tipos de error, tres tratamientos

TipoEjemploStatusQué ve el usuario
De validación Falta el título, la fecha no es fecha 400 El detalle, campo por campo
De negocio El turno se superpone con otro 409 El motivo, en lenguaje humano
Inesperado Se cayó la base, hay un bug 500 Un mensaje genérico. El detalle va al log, no a la pantalla
// lib/errores.ts export class ErrorDeNegocio extends Error { constructor(mensaje: string, public readonly status = 409) { super(mensaje); } } // lib/db/turnos.ts — la regla vive acá, no en el endpoint export async function crearTurno(datos: CrearTurnoInput, usuarioId: string) { const superpuesto = await prisma.turno.findFirst({ where: { profesionalId: datos.profesionalId, fecha: datos.fecha }, }); if (superpuesto) { throw new ErrorDeNegocio("Ese profesional ya tiene un turno a esa hora"); } return prisma.turno.create({ data: { ...datos, creadoPorId: usuarioId } }); }

Que la regla viva en lib/db/ y no en el endpoint importa: mañana el mismo turno se puede crear desde un formulario, desde un import masivo o desde una app móvil. La regla se aplica una sola vez, en el lugar por donde pasan todos.

Defensa en profundidad

Fíjense que la superposición está chequeada dos veces: en el dominio y con un @@unique en la base (clase 3). No es redundancia inútil: si dos usuarios crean el mismo turno en el mismo instante, el chequeo del dominio puede pasar en ambos y solo la base lo impide.

3. Testing: qué se testea cuando el tiempo es poco

No vamos a buscar cobertura del 100%: en 16 clases no tiene sentido. Vamos a testear lo que rompe el negocio si falla.

Sí testear

  • Las reglas de negocio del spec.md
  • Los casos borde: vacío, límite, duplicado, fecha pasada
  • Los schemas de Zod (rápidos y valiosos)
  • Lo que ya se rompió una vez

No testear (todavía)

  • Que Prisma sepa hacer un create
  • Que React renderice un div
  • Getters y setters triviales
  • Código que va a cambiar la semana que viene
El reparto correcto con la IA

Ustedes piensan el caso borde; la IA escribe el test. La IA es excelente generando los tres casos obvios y pésima imaginando el cuarto, que es el que importa: "¿qué pasa si el turno se cancela mientras otro usuario lo está confirmando?".

Pídanle: "escriban el test de este caso: …", no "escriban tests para este archivo".

4. Decisiones y trade-offs

DecisiónOpción AOpción BQué hacemos
Dónde vive la regla de negocio En el endpoint: se lee de corrido En lib/db/: se aplica siempre B. El endpoint solo orquesta
Qué devolver en un error Todo el detalle: más fácil de depurar Genérico en 500, detallado en 400/409 B. El stacktrace va al log
Validar en el cliente Sí: mejor experiencia No: menos código duplicado Sí, con el mismo schema. Sin duplicar reglas

5. Taller

  1. Escribir la Definition of Done del equipo en el README. Mínimo 5 criterios verificables.
  2. Implementar ErrorDeNegocio y mover al menos 2 reglas de negocio de la spec a lib/db/.
  3. Manejo de errores consistente en todos los endpoints: 400, 409, 404 y 500 genérico.
  4. Escribir 3 tests: uno de un schema, uno de una regla de negocio, uno de un caso borde que se les ocurra a ustedes (no a la IA).

Entregable de la clase

  • Definition of Done escrita en el README.
  • Al menos 2 reglas de negocio implementadas en la capa de dominio.
  • Errores tipados: 400, 404, 409 y 500 genérico, todos verificables con Postman.
  • 3 tests pasando, uno de ellos de un caso borde propio.
  • Ningún error interno de la base llega al cliente.
