El sistema bajo carga: concurrencia, caching y producción

Objetivo

El sistema anda cuando lo usan ustedes. Hoy vemos qué pasa cuando lo usan muchos a la vez: qué se rompe, qué se pone lento, y cómo se enteran antes que el usuario.

  • 5 min Standup
  • 5 min Metodología: programación paralela y concurrencia
  • 25 min Concurrente vs. paralelo · race conditions · caching · observabilidad
  • 15 min Demo: cazar un waterfall y una consulta N+1
  • 50 min Taller: medir, corregir y dejar producción en condiciones
  • 15 min Code review del equipo
  • 5 min Cierre
Esto que leyeron, hoy lo hacen así

La lectura distingue concurrente de paralelo y habla de multihilo en C/C++. Su servidor no maneja hilos a mano, pero vive exactamente esos problemas: concurrencia cuando dos usuarios tocan el mismo dato en el mismo instante, y paralelismo cuando hacen tres consultas que podrían haber salido juntas y salieron en fila.

Hoy encuentran las dos cosas en su propio código.

1. Concurrencia: dos usuarios, el mismo instante

Este código parece correcto y falla en producción cada tanto, de forma imposible de reproducir a mano:

const existe = await prisma.turno.findFirst({ where: { profesionalId, fecha }, }); if (existe) throw new ErrorDeNegocio("Ya hay un turno a esa hora"); await prisma.turno.create({ data: { profesionalId, fecha } });
Usuario A Usuario B ──────────────────────────────────────────────────── findFirst → no hay nada findFirst → no hay nada create ✅ create ✅ ← dos turnos a la misma hora Entre el chequeo y la escritura hay una ventana. Ese hueco es una RACE CONDITION.

Las tres formas de cerrarlo, de más simple a más compleja:

CómoCuándo
Una restricción @@unique en la base y capturar el error Casi siempre. La base es el único punto por el que pasan todos. Ya la pusieron en la clase 3
Una transacción ($transaction) Cuando varias escrituras tienen que pasar todas o ninguna: descontar stock y crear el pedido
Bloqueo explícito de la fila Casos raros de alta contención. En este proyecto, probablemente no haga falta
Por qué esto sale casi siempre mal cuando lo escribe una IA

"Verificar y después crear" es el patrón más natural de escribir, y es el que genera cualquier asistente si no le dicen otra cosa. Funciona en todas las pruebas y falla en producción una vez cada mil. Es la pregunta estrella de la defensa final: "¿qué pasa si dos usuarios hacen esto al mismo tiempo?".

2. Paralelismo: lo que espera sin necesidad

En fila (mal)

const a = await pedirA(); const b = await pedirB(); const c = await pedirC(); // 300 + 300 + 300 = 900ms

En paralelo (bien)

const [a, b, c] = await Promise.all([ pedirA(), pedirB(), pedirC(), ]); // 300ms

Se detecta en la pestaña Network: si las barras están escalonadas en vez de arrancar juntas, hay un waterfall. Solo se secuencia cuando un pedido realmente necesita el resultado del anterior.

La consulta N+1

const turnos = await prisma.turno.findMany(); // 1 consulta for (const turno of turnos) { turno.profesional = await prisma.profesional.findUnique({ // + N consultas where: { id: turno.profesionalId }, }); } // 50 turnos = 51 viajes a la base

Se arregla con un include: una sola consulta que trae todo. Con 10 registros de prueba no se nota; con 500 en producción, el endpoint tarda segundos. Por eso la tarea de la clase pasada era cargar datos de verdad.

3. Caching: qué guardar y cuándo tirarlo

Cachear es guardar una copia para no volver a pedirla. El problema nunca es guardar: es saber cuándo la copia dejó de valer.

El usuario crea un registro ↓ El POST responde 201 ↓ ¿El listado se entera? ← acá está el bug del 90% de los casos ↓ revalidatePath("/turnos") (Server Actions) queryClient.invalidateQueries(...) (TanStack Query) ↓ El listado se vuelve a pedir y muestra el registro nuevo

Regla: toda mutación declara qué invalida. Si no lo hace, la pantalla miente.

Server state vs. client state

Server state

La lista de turnos, el usuario, los pedidos.

La verdad está en la base; ustedes tienen una copia que puede quedar vieja y que otro usuario puede cambiar.

Client state

El modal abierto, el filtro elegido, el paso del wizard.

La verdad está en la pantalla. Nunca queda desactualizado y nadie más lo toca.

El bug clásico

Copiar server state a un useState y modificar la copia. Ahora hay dos verdades y se desincronizan: de ahí salen los "a mí no me aparece el registro que acabo de crear".

Si hace falta manejar server state en el cliente (búsquedas, filtros, refetch), la herramienta es TanStack Query. Si no hace falta, no la agreguen: eso también se evalúa.

4. Producción: enterarse antes que el usuario

El peor escenario no es que algo falle: es que falle y nadie se entere hasta que un usuario avisa por WhatsApp.

  • CI en verde. El pipeline corre en cada PR: tipos, lint y tests. Rojo significa que no se mergea, sin excepciones — un CI que se ignora es peor que no tenerlo.
  • Logs con contexto. console.error("error") no sirve: qué operación, qué usuario, qué datos. Y nunca loguear contraseñas, tokens ni datos personales.
  • Mirar el panel de Vercel. Los errores de las funciones están ahí desde la clase 1. ¿Alguien los miró alguna vez?
  • Medir con Lighthouse, sobre producción y no sobre localhost.

Checklist de seguridad antes del cierre

  • Ningún secreto en el repo ni en variables NEXT_PUBLIC_.
  • Todos los endpoints que modifican datos verifican sesión y permisos en el servidor.
  • Los listados filtran por lo que el usuario puede ver, no ocultan en el cliente.
  • Toda entrada externa se valida con Zod, incluidas las respuestas de terceros y del modelo de IA.
  • Los errores internos no llegan al cliente.
  • La rama main sigue protegida.
El mejor uso de IA de toda la materia

Revisar 40 archivos buscando un patrón es tedioso para una persona y trivial para una IA. Preguntale: "¿qué endpoints no verifican autorización?", "busquen consultas sin límite", "¿hay algún secreto expuesto al cliente?", "¿dónde hay un chequeo seguido de una escritura que podría tener race condition?".

Y después verificá cada hallazgo. Van a aparecer tres tipos: problemas reales, cosas irrelevantes y alarmas inventadas. Separarlas es el trabajo — y es exactamente lo que se evalúa en la defensa final.

5. Taller

  1. Buscar en el proyecto un chequeo seguido de escritura y cerrarlo con una restricción de base o una transacción.
  2. Abrir Network con datos reales cargados: cazar un waterfall o un N+1, corregirlo y anotar el antes y el después.
  3. Verificar que todas las mutaciones invaliden lo que corresponde: crear → aparece, editar → cambia, borrar → desaparece, sin recargar a mano.
  4. Auditoría de seguridad con la checklist, asistida por IA y verificada a mano. Cada hallazgo real, un issue.
  5. Lighthouse sobre producción: medir, arreglar lo más grave, volver a medir. Dejar el CI en verde.

Entregable de la clase

  • Al menos una race condition cerrada, con la solución explicada en el PR.
  • Un waterfall o N+1 corregido, con la medición antes y después.
  • Todas las mutaciones invalidan correctamente.
  • Auditoría de seguridad hecha y hallazgos reales corregidos.
  • Lighthouse medido sobre producción, documentado.
  • CI en verde en el último PR.
