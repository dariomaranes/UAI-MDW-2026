1. Dónde estamos: la letra que faltaba

La semana pasada cerró el backend. Ese hito está cumplido: CRUD, validaciones, reglas de negocio, autenticación con dos roles y un servicio externo, todo en producción. Hoy empieza otra cosa.

El Parcial I sigue siendo del backend

Es el 06/10, y se defiende lo de las clases 1 a 7. Lo que construyan hoy no suma en la rúbrica — pero sí puede restar, si al agregar pantallas rompen algo que andaba. La regla de la semana: que la URL pública siga respondiendo todos los días.

Ustedes ya escribieron React y no se enteraron

Abran app/page.tsx. Eso es un componente de React: una función que devuelve algo parecido a HTML. Está ahí desde la clase 1 y en la clase 6 pasó a mostrar el listado de mascotas de quien inicia sesión.

Lo que cambia hoy no es empezar a usar React. Es entender dónde se ejecuta cada componente, que es lo único de este tema que se puede hacer mal en serio.

Todo React que hace falta hoy

Son cuatro cosas, y las cuatro están en archivos que ya tienen abiertos. El resto de React aparece cuando haga falta.

1. Un componente es una función que devuelve JSX. No hay clases ni nada más. Los tres del proyecto son iguales:

app/page.tsx export default async function Home() app/mascotas/[id]/page.tsx export default async function DetalleMascota({ params }) components/buscador-mascotas.tsx export function BuscadorMascotas({ mascotas })

El default de los dos primeros no es un capricho: Next exige que el archivo de una página exporte su componente así. Los componentes sueltos se exportan como cada uno quiera.

2. Las props son los parámetros de esa función. Se pasan como si fueran atributos de HTML y llegan como un objeto. Las dos puntas:

// app/page.tsx — quién las manda <BuscadorMascotas mascotas={mascotas} /> // components/buscador-mascotas.tsx — quién las recibe export function BuscadorMascotas({ mascotas }) { ... }

3. Las llaves quieren decir "acá adentro va JavaScript". Esta línea sola explica JSX entero —texto suelto, valores entre llaves, y un ternario adentro—:

{usuario.nombre} · {esVeterinario ? "Veterinario" : "Dueño"}

4. Y el key, que van a ver y conviene despachar. Cuando se pinta una lista, React pide un valor distinto por elemento para saber cuál es cuál. Se usa el id y se sigue:

<li key={mascota.id}>
React y Next.js, de una vez

React es una librería para escribir componentes. No sabe de URLs, ni de servidor, ni de base de datos.

Next.js es un framework construido encima de React que pone todo eso.

No se elige entre los dos: ustedes escriben React, y Next decide dónde corre. Es lo mismo que se dijo en la clase 1, y hoy recién se ve para qué servía saberlo.

2. Metodología: MVC y AJAX diez minutos

Las tres letras, y dónde viven en su repositorio

El material define MVC como un patrón que separa una aplicación en tres componentes lógicos. La definición es correcta y no hace falta discutirla. Lo que sí vale la pena es ubicarla:

LetraQué dice el materialDónde está en su proyecto
Modelo Toda la lógica relacionada con los datos prisma/schema.prisma, lib/db/, lib/schemas/
Vista Toda la lógica de la interfaz de usuario Postman. Hasta hoy, literalmente
Controlador Interfaz entre modelo y vista; procesa las solicitudes app/api/**/route.ts

La fila del medio es el chiste de las últimas siete clases y también la razón por la que el backend les salió bien: construir el modelo y el controlador sin vista obliga a que las reglas estén del lado correcto. Un sistema que se probó con Postman no puede tener la validación escondida en un formulario.

Dónde el material se queda corto

En el texto, el controlador "procesa toda la lógica comercial". En su proyecto eso no es cierto, y a propósito: el handler valida, autoriza, delega y responde, pero no decide. Las reglas viven en lib/estado-sanitario.ts y en los schemas. Es la separación de la clase 5, y son cuatro capas donde MVC nombra tres. El patrón es una guía, no un molde.

AJAX, y por qué hoy se hace al revés

La segunda mitad del material describe AJAX sin decir nunca qué quiere decir la sigla: Asynchronous JavaScript And XML. Código JavaScript incrustado en la página que le manda solicitudes al servidor con XMLHttpRequest y sigue andando mientras espera la respuesta, para no tener que recargar todo. En 2005 eso era una revolución. La secuencia era:

AJAX (2005) el servidor manda una página VACÍA el navegador la dibuja el navegador pide los datos ← un segundo viaje el navegador vuelve a dibujar ← y acá recién se ve algo

Ese segundo viaje es el precio. Se paga siempre, y se paga en el peor momento: cuando la persona ya está mirando una pantalla vacía. Durante quince años la industria lo dio por inevitable, y la discusión pasó a ser cuál librería lo disimulaba mejor —el material propone elegir entre jQuery, Mootools y Ext JS—. Ninguna de las tres sacaba el viaje: lo hacían más cómodo de escribir.

Los Server Components dan vuelta la pregunta. Si el componente ya corre en el servidor, no tiene a quién pedirle nada: la base está ahí al lado.

HOY el servidor lee la base el servidor manda la página CON los datos adentro el navegador la dibuja ← y ya está

Volvimos a lo de 1999: el servidor manda la página hecha. Con una diferencia que no es menor —la navegación sigue sin recargar—, y ahí está toda la historia en un renglón: quedó lo que AJAX buscaba y se fue lo que cobraba a cambio. Y la pregunta del material —¿qué framework Ajax elegir?— dejó de existir dos veces: primero porque ganó React, después porque para leer datos ya no hace falta pedirlos desde el navegador.

La X de AJAX es mentira

XML perdió contra JSON casi enseguida, así que durante veinte años la industria le dijo "AJAX" a una técnica donde la X no se usaba. Lo que ustedes hacen con res.json() es exactamente eso.

Dos datos más, que dicen algo sobre cómo se mueve esta industria. La sigla la inventó Jesse James Garrett —el "JJ Garrett" que nombra el PDF— en un ensayo de febrero de 2005. No inventó la técnica: le puso nombre a algo que ya se estaba haciendo, y por eso explotó. Y el objeto que lo hacía posible, XMLHttpRequest, lo había hecho Microsoft en 1999 para que Outlook anduviera en el navegador: la herramienta era seis años más vieja que el nombre.

3. Qué corre dónde, y el fetch que no va

En el App Router todo componente es un Server Component salvo que digan lo contrario. No hay que escribir nada para que lo sea: es el default, y el default es el bueno.

Qué significa "corre en el servidor"

PuedeNo puede
Ser async y esperar a la base Acordarse de algo entre un click y el siguiente
Leer process.env con secretos Responder a onClick o onChange
Leer la sesión y llamar a lib/db/ Tocar window, localStorage o el DOM

La columna de la izquierda tiene una consecuencia de seguridad que conviene decir en voz alta: el código de un Server Component nunca llega al navegador. Lo que viaja es el resultado. Por eso puede leer una credencial sin exponerla, y por eso el STORAGE_KEY de la clase pasada sigue estando a salvo.

El error que van a cometer esta semana

Ustedes tienen GET /api/mascotas/:id andando. El reflejo es usarlo desde la página:

// ✗ la página pidiéndose los datos a sí misma const res = await fetch("https://mi-app.vercel.app/api/mascotas/" + id); const mascota = await res.json();

Compila, anda, y está mal. Este componente ya está en el servidor: salir por HTTP para volver a entrar es salir por la puerta y volver por la ventana.

con fetch página (servidor) ──red──→ su propia API ──→ base sin fetch página (servidor) ─────────────────────────→ base

Lo que cuesta el viaje del medio

  • Una ida y vuelta de red que no le sirve a nadie.
  • La cookie de sesión no viaja sola: un fetch que sale del servidor no lleva las del navegador, y hay que reenviarla a mano.
  • Hay que escribir la URL absoluta, que cambia entre localhost y producción.
  • El error deja de ser un null y pasa a ser un status que hay que interpretar.

Lo que se hace en cambio

const mascota = await obtenerMascotaVisiblePara( id, usuario.id, usuario.rol );

La misma función que usa el endpoint. Sin red, sin cookie que reenviar, sin URL, y con los tipos de Prisma intactos.

¿Y entonces para qué queda la API?

Para quien no es esta página: la aerolínea que verifica un certificado, Postman, la app móvil que quizás exista, el equipo que integre con ustedes. Un endpoint público y un Server Component son dos consumidores del mismo modelo, no dos capas apiladas. Los dos llaman a lib/db/; ninguno llama al otro.

Esa es también la respuesta a "¿tiro la API entonces?". No: es lo que se defiende el 06/10, y es lo único que un tercero puede consumir.

4. Cuándo un componente se vuelve de cliente

La regla entra en un renglón, y no tiene excepciones interesantes:

¿necesita ESTADO, EVENTOS o APIs del navegador? NO → Server Component. No se escribe nada, es el default. SÍ → "use client", y lo más chico posible.
Qué quieren hacer¿Cliente?Por qué
Listar mascotasNoSe dibuja una vez y no cambia
Un link a otra pantallaNo<Link> ya resuelve la navegación
Un buscador que filtra mientras se escribeSíTiene que recordar lo escrito entre una tecla y la otra
Un menú que se abre y se cierraSíAbierto o cerrado es estado
Un formulario que manda datosDependeCon Server Actions, no hace falta. Lo ven en la clase 11

"use client" no es "solo navegador": es "también navegador"

El nombre engaña. Un componente de cliente también se ejecuta en el servidor, una primera vez, para generar el HTML inicial. Recién después viaja al navegador, donde React lo vuelve a ejecutar y le engancha la interactividad encima del HTML que ya estaba dibujado.

¿Corre en el servidor?¿Corre en el navegador?
Server Component Sí, una vez Nunca. El código ni siquiera viaja
Client Component Sí, una vez Sí, y otra vez cada vez que cambia el estado

Por eso la pantalla no aparece en blanco mientras se descarga el JavaScript. Y por eso existe el error que está unos párrafos más abajo: si el componente corre dos veces y las dos no dan lo mismo, React se da cuenta y avisa.

"use client" marca una frontera, no un archivo

La otra parte que se entiende mal. La directiva no afecta solo al archivo donde está escrita: todo lo que ese archivo importe se va al navegador con él, y lo que esos archivos importen también. La frontera la corren los import.

Al revés no pasa nada: el archivo que usa un componente de cliente no se vuelve de cliente. La home sigue siendo de servidor aunque renderice el buscador, y puede seguir poniendo componentes de servidor antes y después de él.

La frontera arriba de todo

// app/page.tsx "use client"; // ← por un <input>

El listado, el encabezado, el pie y todo lo que importen se van al navegador. Y la página ya no puede ser async ni leer la base: habría que volver al fetch del punto anterior.

La frontera lo más abajo posible

// components/buscador-mascotas.tsx "use client";

Solo el buscador viaja. La página sigue siendo de servidor, sigue leyendo la base directo, y le pasa los datos ya resueltos.

Qué puede cruzar la frontera

Las props van del servidor al navegador serializadas, así que tienen que ser datos: strings, números, booleanos, arrays, objetos planos. Una función no cruza. Una instancia de una clase, tampoco.

El error de las fechas, que van a ver sí o sí

En la base no dice "1 de septiembre": dice un instante universal. Qué día es ese instante depende de dónde estés parado. Esta es la fecha de nacimiento de Laika, la del proyecto de referencia, formateada en los dos lugares donde el componente va a correr:

valor en la base : 2023-09-01T02:41:52.085Z servidor (UTC) : 1 de septiembre de 2023 navegador (AR) : 31 de agosto de 2023 ← UTC−3: todavía es el día anterior

Las dos están bien. El problema es que el mismo componente las calculó a las dos: React generó el HTML en el servidor con 1 de septiembre, y al volver a ejecutarse en el navegador le dio 31 de agosto. No coinciden, y avisa.

Y el aviso es lo de menos: el usuario ve la fecha cambiar delante de los ojos cuando termina de cargar el JavaScript.

La solución no es pelear con el aviso: es formatear una sola vez, del lado del servidor, y mandar el texto ya armado. Si el navegador no tiene ninguna cuenta que rehacer, no puede darle distinto. Por eso en el código de hoy la fila lleva nacimiento: string y no fechaNacimiento: Date.

5. El caso completo: la pantalla de una mascota

Dos archivos nuevos y una modificación. El repositorio de referencia los tiene, y el recorrido de la clase es por ahí.

app/mascotas/[id]/page.tsx ← Server Component. La pantalla nueva. components/buscador-mascotas.tsx ← "use client". El primero del proyecto. app/page.tsx ← ahora delega el listado al buscador.

Dónde va cada archivo, y por qué casi nada es nuevo

La ruta de la pantalla nueva les tiene que sonar, porque vienen escribiendo la misma convención desde la clase 4:

app/api/mascotas/[id]/route.ts → /api/mascotas/laika (clase 4) app/mascotas/[id]/page.tsx → /mascotas/laika (hoy)

La carpeta es la URL, y los corchetes son la parte que cambia. Eso no cambió. Lo único distinto es el nombre del archivo, y con él quién está del otro lado:

ArchivoDevuelveLo consume
route.tsJSONUn programa
page.tsxUna pantallaUna persona

Los dos pueden convivir en la misma carpeta y no se pisan. De hecho conviven: /api/mascotas/laika y /mascotas/laika leen la misma fila, cada uno para su público.

¿Y por qué el buscador no va en app/?

Porque no es una pantalla, es un pedazo de pantalla. Todo lo que vive en app/ tiene una dirección web; el buscador no tiene por qué tener una, nadie va a escribir /buscador en el navegador.

Por eso aparece components/, que es la carpeta nueva de hoy: piezas que se importan, sin URL propia. La regla para saber dónde va algo es esa: ¿esto es una dirección a la que alguien entra, o una parte de otra cosa?

La pantalla de detalle

Tres líneas son toda la clase. El resto es JSX.

const usuario = await obtenerUsuario(); if (!usuario) redirect("/"); const mascota = await obtenerMascotaVisiblePara(id, usuario.id, usuario.rol); if (!mascota) notFound();

La segunda línea es la misma función que usa GET /api/mascotas/:id. No se copió la regla ni se volvió a escribir: la autorización nunca vivió en el endpoint, vive en lib/db/. Por eso la pantalla la hereda completa, y para un dueño la mascota del vecino devuelve null exactamente igual que en la API.

Y la primera muestra algo que conviene tener claro: la misma pregunta se contesta distinto según el borde. Un endpoint responde 401 y corta, porque del otro lado hay un programa. Una pantalla manda al login, porque del otro lado hay una persona. La regla es una sola; la traducción, dos. Es el mismo criterio de responderError en la clase 6.

Qué respondió de verdad, medido

No son los códigos que uno espera: son los que devolvió el servidor.

Situación/api/mascotas/:id/mascotas/:id
Con sesión, mascota propia200200
Sin sesión401307 → /
No existe404404
De otro dueño404404

Las dos últimas filas son iguales a propósito, y eso ya lo decidieron en la clase 6: responder distinto confirmaría que el recurso existe.

El buscador, que sí es de cliente

Acá aparece lo único de React que no vieron nunca. Cuando alguien escribe una letra, el componente tiene que acordarse de lo que lleva escrito y volver a dibujarse con la lista filtrada. Una variable común no alcanza para eso: se pierde en cuanto la función termina, y cambiarla no avisa a nadie.

const [texto, setTexto] = useState(""); // ↑ ↑ ↑ // | | el valor inicial: vacío // | la función para cambiarlo // el valor actual

useState devuelve siempre ese par: el valor y la única forma de cambiarlo. La regla es que el valor no se toca a mano —texto = "otra cosa" no hace nada—: se llama a setTexto(...), y React vuelve a ejecutar el componente con el valor nuevo y redibuja lo que haya cambiado.

Eso es todo lo que necesitan hoy. El resto de React —los otros hooks, los efectos— aparece cuando haga falta, y una buena parte no va a hacer falta nunca: en el App Router muchas cosas que antes se resolvían con hooks ahora se resuelven en el servidor.

const termino = texto.trim().toLowerCase(); const visibles = termino ? mascotas.filter((m) => m.nombre.toLowerCase().includes(termino)) : mascotas;

El filtro no le pregunta nada al servidor. Las mascotas ya están ahí: llegaron con el HTML, en el mismo viaje. Escribir una letra no genera ningún request, y por eso responde al instante.

Es el contraejemplo perfecto del reflejo AJAX. Con la mentalidad del material, cada tecla dispararía un XMLHttpRequest a /api/mascotas?buscar=.... Abran la pestaña Network del navegador mientras escriben: no pasa nada. Eso es lo que hay que mirar.

Hasta dónde vale filtrar en el cliente

Vale porque la lista entera cabe en la pantalla: lib/db/ trae como mucho 50 filas. Con diez mil, la decisión se invierte: no se le mandan diez mil filas al navegador para que descarte 9.990. Ahí filtrar vuelve a ser trabajo del servidor.

No es una regla de React: es la misma pregunta de siempre, ¿quién tiene los datos y cuántos son?

6. Decisiones: qué se gana y qué se resigna

DecisiónSe ganaSe resigna
Server Components por defecto Un viaje de red menos, la base y los secretos a mano, menos JavaScript en el navegador Hay que tener presente dónde corre cada cosa. El error se ve recién al compilar
La frontera lo más abajo posible Al navegador viaja solo lo que necesita interactuar Más archivos chicos, y hay que decidir dónde va el corte
Formatear en el servidor Una sola verdad para la fecha, y ningún aviso de React por HTML que no coincide La fila deja de tener los tipos del dominio y pasa a ser texto para mostrar
Filtrar en el cliente Respuesta instantánea, cero requests Solo sirve mientras la lista sea chica

7. Qué le pedimos a la IA (y qué no)

Este es el tema donde la IA más se equivoca de toda la materia, y por una razón concreta: fue entrenada con años de React anterior al App Router. En ese React todo corría en el navegador, así que la única forma de conseguir datos era pedirlos por la red. El modelo escribe lo que más vio, y lo que más vio es eso.

Por eso van a recibir mucho código que trae los datos desde el navegador aunque el componente ya esté en el servidor. No siempre se reconoce a simple vista, así que acá está la forma que tiene:

// ✗ lo que les va a proponer la IA "use client"; // ← 1. la página entera al navegador export default function Pagina() { const [mascotas, setMascotas] = useState([]); // ← 2. una lista vacía useEffect(() => { // ← 3. "cuando la página aparezca..." fetch("/api/mascotas") // ...pedile los datos al servidor .then((r) => r.json()) .then(setMascotas); }, []); return <ul>{/* ... */}</ul>; }

useEffect es otro hook, y no lo vimos ni hace falta que lo vean hoy. Alcanza con reconocer el dibujo: la pantalla arranca vacía y después sale a buscar los datos. Eso es el AJAX de la lectura, veinte años después. Su versión son dos líneas y no necesita ninguna de las tres cosas de arriba:

// ✓ lo que corresponde const mascotas = await listarMascotasDeDueno(usuario.id);

Pedile

  • El JSX repetitivo de una tabla o una lista.
  • Clases de Tailwind para algo que ya sabés cómo tiene que quedar.
  • Estados vacíos: "no hay resultados", "todavía no cargaste ninguna".
  • Que te explique un error de React que no entendés, con el archivo a la vista.

No le delegues

  • Decidir qué componente es de cliente. Es la decisión de la clase.
  • Dónde va la frontera "use client".
  • Cómo llegan los datos a la pantalla.
Tres chequeos antes de aceptar código de pantalla
  1. ¿Los datos se piden con un fetch, en vez de con un await a lib/db/? Es el error del punto 3, escrito por otro. Si además el fetch apunta a la API de ustedes, es el viaje de ida y vuelta que no va.
  2. ¿Puso "use client" arriba de la página entera? Preguntate qué necesita acordarse de algo o reaccionar a un click. Casi siempre es un solo elemento, y la directiva va en ese, no en la página.
  3. ¿La consulta lleva el id de la sesión? Una pantalla que muestra datos de otro no falla: se ve perfecta. Es el error más caro y el único que no avisa.

8. Taller

Dos pantallas sobre el sistema de ustedes. Nada de diseño todavía —eso es la clase 10—: hoy importa que los datos lleguen bien y con los permisos correctos.

  1. El listado de su entidad principal, como Server Component, leyendo de lib/db/ con el id de la sesión adentro de la consulta. Si ya lo tenían de la clase 6, revisen que no haya ningún fetch a su propia API.
  2. La pantalla de detalle en app/<entidad>/[id]/page.tsx, reusando la misma función de autorización que usa su endpoint. Con notFound() cuando no corresponde, y sin inventar un mensaje distinto para "no existe" y "no es tuya".
  3. Un solo componente de cliente, el más chico que puedan. Un buscador, un filtro por estado, un ordenamiento. Con "use client" en ese archivo y en ninguno más.
  4. Probar el caso que importa: copien la URL de detalle de un registro propio, abran una ventana de incógnito y péguenla. Tiene que mandarlos al login, no mostrar el dato. Después inicien sesión con otra cuenta y péguenla de nuevo: tiene que dar 404.

Entregable de la clase

  • Dos pantallas propias —listado y detalle— leyendo de lib/db/, sin ningún fetch a la API propia.
  • La consulta del listado y la del detalle llevan el id de la sesión, igual que en los endpoints.
  • notFound() y redirección al login resueltos, con el mismo criterio que la API.
  • Un componente con "use client", justificable en una frase.
  • Todo funcionando en producción, no solo en localhost.
  • PR revisado y aprobado por un integrante que no lo escribió.
