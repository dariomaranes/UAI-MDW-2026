Autenticación y autorización

Objetivo

Saber quién entra al sistema y qué puede hacer. Es el tema donde el código "que parece correcto" es más peligroso, y por eso es la clase donde menos se acepta output de IA sin leer.

  • 5 min Standup
  • 5 min Metodología: monolitos vs. arquitectura orientada a servicios
  • 25 min Autenticación vs. autorización · sesión · roles
  • 15 min Demo: romper mi propia app con Postman
  • 50 min Taller: login, roles y protección real
  • 15 min Code review del equipo
  • 5 min Cierre
Esto que leyeron, hoy lo hacen así

La lectura es sobre monolitos vs. servicios. La autenticación es la primera decisión real de ese tipo que toma el equipo: ¿la resuelven adentro de su aplicación con Auth.js, o la delegan a un servicio de identidad externo? Las dos son válidas. Lo que se evalúa es que puedan justificar cuál eligieron —y eso va a un ADR, junto con el riesgo de equivocarse.

1. Dos preguntas distintas

Autenticación — ¿quién son?

Verificar identidad: login, contraseña, Google, magic link.

Se resuelve una vez, al entrar. Falla → 401.

Autorización — ¿pueden hacer esto?

Verificar permisos sobre una acción concreta.

Se resuelve en cada request. Falla → 403.

El 90% de los problemas de seguridad de sistemas como los suyos no están en la autenticación —que suele venir resuelta por una librería— sino en la autorización, que la escribe cada equipo a mano, endpoint por endpoint.

2. Cómo funciona una sesión

1. El usuario manda email + contraseña ↓ 2. El servidor verifica y crea una SESIÓN ↓ 3. Devuelve una cookie firmada (httpOnly: el JS no la puede leer) ↓ 4. El navegador la manda sola en cada request siguiente ↓ 5. El servidor la verifica y sabe quién es el usuario La cookie NO dice "soy admin". Dice "soy el usuario X", y el servidor busca en SU base qué puede hacer X.
Por qué el rol no viaja en el cliente

Si el rol viniera en el request, cualquiera lo cambia a ADMIN. El rol se lee siempre de la sesión, del lado del servidor. Lo mismo con el userId: nunca sale del body.

El contrato en este proyecto

// lib/auth.ts const usuario = await requerirUsuario(); // 401 si no hay sesión const admin = await requerirUsuario("ADMIN"); // 403 si el rol no alcanza // En TODO endpoint que necesite saber quién llama: export async function DELETE(request, { params }) { const usuario = await requerirUsuario(); const turno = await obtenerTurno(params.id); if (!turno) return NextResponse.json({ error: "No existe" }, { status: 404 }); // Autorización a nivel del RECURSO, no solo del rol: // ser usuario no habilita a borrar el turno de otro. if (turno.creadoPorId !== usuario.id && usuario.rol !== "ADMIN") { return NextResponse.json({ error: "No autorizado" }, { status: 403 }); } await eliminarTurno(params.id); return new Response(null, { status: 204 }); }

Ese chequeo del medio —"¿este recurso es propio?"— es el que más se olvida y el que más se pregunta en la defensa.

3. Demo: romper mi propia app

En vivo, sobre el proyecto de referencia: la UI esconde el botón "eliminar" a los usuarios comunes. Parece seguro. Entonces abrimos Postman, copiamos la cookie de sesión de un usuario común y mandamos el DELETE a mano.

Esconder el botón no es seguridad

La UI es una sugerencia. La seguridad está en el servidor o no está. En el Parcial I se prueba exactamente esto con Postman.

Checklist de autorización (se usa en la revisión)

  • Todo endpoint que modifica algo exige sesión.
  • El userId sale de la sesión, nunca del body ni de la query.
  • Además del rol, se verifica la pertenencia del recurso.
  • Los listados filtran por lo que el usuario puede ver (no traen todo y ocultan en el cliente).
  • 401 y 403 se distinguen correctamente.
  • Ningún secreto tiene el prefijo NEXT_PUBLIC_.

4. Decisiones y trade-offs

DecisiónA favorEn contra
Auth.js (lo que usamos) Gratis, en el repositorio, ven cómo funciona, aprenden el mecanismo Más configuración inicial
Servicio externo (Clerk, Firebase, Auth0) Funciona en 10 minutos, trae UI hecha Caja negra, dependen de un tercero, cuesta plata al escalar
Contraseña propia No dependen de nadie Hashing, recupero, políticas: mucha superficie para equivocarse
OAuth (entrar con Google) Sin contraseñas que proteger, menos fricción Dependés del proveedor; hay que configurar credenciales

Recomendación: Auth.js con OAuth de Google. Sin contraseñas que gestionar y el mecanismo queda a la vista. Si el equipo se traba más de 30 minutos en la configuración, se cambia a un servicio externo y se documenta como ADR: el proyecto no puede quedar frenado en el login.

5. Qué le pedimos a la IA (y qué no)

La regla de esta clase

Todo lo que la IA escriba de auth se lee línea por línea. No porque escriba mal, sino porque acá un error no se nota: la app funciona igual, y el agujero aparece cuando alguien lo busca.

Deleguen

  • La configuración inicial de Auth.js
  • El formulario de login y sus estados
  • Los tipos de la sesión
  • Auditar: "¿qué endpoint no verifica permisos?"

Escriban y revisen ustedes

  • Quién puede hacer qué (la matriz de permisos)
  • Cada chequeo de pertenencia del recurso
  • Qué campos se exponen de cada usuario
  • Qué pasa cuando expira la sesión

6. Taller

  1. Login funcionando: registro/ingreso, sesión persistente, logout.
  2. Implementar obtenerUsuario y requerirUsuario en lib/auth.ts (el template ya trae el contrato) y usarlas en todos los endpoints.
  3. Escribir la matriz de permisos en docs/spec.md: filas = acciones, columnas = roles, celdas = sí/no/solo propios.
  4. Atacar el proyecto de otro equipo con Postman: intentar hacer algo que no deberían poder. Quien encuentra un agujero lo reporta como issue en el repositorio del otro equipo.

Escribir el ADR del riesgo de autorización antes de cerrar el PR.

Entregable de la clase

  • Login y logout funcionando en producción.
  • 2 roles con permisos efectivamente distintos.
  • Todos los endpoints que modifican datos verifican sesión y permisos en el servidor.
  • Chequeo de pertenencia del recurso donde corresponde.
  • Matriz de permisos documentada en la spec.
  • ADR del riesgo de autorización.
  • Un intento de ataque documentado contra otro equipo (y el propio, corregido).
